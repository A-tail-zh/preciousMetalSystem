# 用 Codex 开发与维护贵金属加工系统

本文参考你粘贴的《Codex 从零搭建一个完整项目——全流程实战记录》的组织方式，结合当前贵金属加工系统，按“项目规划 → 分阶段步骤 → Prompt → 验收 → 问题修正”整理。

项目已经存在，以下Prompt是帮助理解、复现和后续维护的任务模板，不是当时开发对话的逐字记录，也不是要求重新生成整个仓库。除明确标注的现有实现外，模板中的“请实现”需要在你实际发起任务后才执行。本文不统计无法可靠追溯的开发耗时、模型费用、生成文件数或代码行数。

适用目录：`D:/leo/heavyMetalSystem`。源码核对基准：2026年10月15日。后续修改应以实际代码、数据库最终结构和测试结果更新本文。

# 一 项目规划

## 项目定位

项目：贵金属加工生产管理系统。

主要管理工厂、产线、产品、基础物料、加工工序、人员角色、报价、生产工单、仓储出入还库、加工损耗、预警、日志和数据看板。

核心业务链：

```text
基础资料配置
  → 产品绑定有顺序的工序和每件理论损耗
  → 创建工单并保存产品、工序快照
  → 审核通过
  → 生产出库领料，后台自动关联未结算加工批次
  → 加工后登记半成品/成品产出，必要时登记余料还库
  → 确认本次产出和回料齐全，结算
  → 生成报工与损耗判断，超出理论值才预警
  → 后续工序继续加工或成品对外出库
```

报价是独立的计算与保存流程，不能把保存报价直接理解成创建生产工单。

## 技术栈

| 层次 | 当前技术 | 作用 |
| --- | --- | --- |
| 后端基础 | 若依体系、Java、Spring Boot 4.1.0 | 启动应用、提供API和基础管理能力 |
| 编译级别 | backend/pom.xml配置Java 17 | 不等同于本机安装JDK的版本 |
| 持久化 | MySQL、MyBatis、JdbcTemplate | 保存业务数据、关联查询与事务 |
| 会话与缓存 | Redis | 保存登录会话、验证码等 |
| 数据迁移 | Flyway | 按版本维护数据库结构 |
| 认证授权 | Spring Security、JWT、BCrypt | 身份识别、权限和密码校验 |
| 前端 | Vue 3.5、TypeScript 5.6、Vite 6.4 | 页面与开发构建 |
| 页面能力 | Element Plus、Vue Router、Pinia、Axios、ECharts | 表单、路由、状态、请求和图表 |
| 验证 | 后端测试、vue-tsc、Playwright | 业务、类型与浏览器回归 |

这是一套前后端分离的模块化单体项目，不能因为后端有多个Maven模块就称为微服务。

## 后续使用Codex的总原则

从已有实现继续做增量修改。先确定本次要改变的行为，再查对应文件和规则；复杂业务先设计再实现。UI排版、业务计算、数据库迁移与数据清理应分别描述，避免一句“顺便优化一下”带来无法审查的扩展。

## Step 2 核心配置与启动

**配置说明**

主要后端配置在 `backend/ruoyi-admin/src/main/resources/` 的application.yml、application-druid.yml、application-metal.yml。前端配置在 `frontend/vite.config.ts` 和对应环境文件。

| 配置项 | 说明 |
| --- | --- |
| MYSQL_URL | JDBC地址，包括主机、端口、数据库、编码及时区 |
| MYSQL_USER / MYSQL_PASSWORD | 应用数据库账号与密码，使用私有环境注入 |
| REDIS_HOST / REDIS_PORT / REDIS_PASSWORD | Redis连接参数 |
| TOKEN_SECRET | JWT签名密钥，不属于前端变量 |
| UPLOAD_PATH | 上传文件目录 |
| ADMIN_PASSWORD_HASH | 初始化迁移使用的管理员密码哈希 |
| VITE_APP_BASE_API | 开发环境为/dev-api，生产环境为/prod-api |

当前本地环境端口：MySQL 3308、Redis 6380、后端8080、前端5173。不要把这些开发端口误认为所有部署环境都固定如此。

配置注意：application-metal.yml的数据源缺省端口3306与Flyway缺省端口3308不同，应显式注入统一的MYSQL_URL。根目录私有.env由本地启动脚本加载，不是Spring Boot自动读取。

**可复制Prompt**

```text
检查当前启动配置，确认数据源与Flyway使用同一个MYSQL_URL，Redis端口一致。
只报告配置键、文件位置和是否一致，不输出密码、令牌或哈希。
解释tools/start-backend.ps1如何加载环境，Vite如何代理到后端。
先报告问题；如需修改，只改配置引用，不写入明文密钥，不改变业务逻辑。
```

**Vite重点**：host为0.0.0.0表示监听网卡；浏览器使用localhost或本机IPv4。5173是前端开发端口；代理把/dev-api前缀去掉后转到8080。生产构建不会携带开发代理，需要部署服务器另配反向代理。

**验收**：前端页面可打开、登录请求能到后端、数据迁移与业务访问同一数据库。另一台电脑通过运行项目电脑的局域网IP访问，不能使用127.0.0.1访问别人的电脑。

## Step 4 认证、密码与会话失效

**实现说明**

登录先检查验证码与账号密码。密码使用BCrypt保存与验证。JWT关联Redis中的登录会话，过滤器继续核对数据库账号状态、工厂及auth_version，不能仅凭JWT签名有效就放行。

密码至少8个字符，并受BCrypt的72字节输入上限约束。修改密码成功后该账号全部会话失效，当前页面也重新登录。普通账号修改手机号同步修改登录账号并重新登录；admin名称不变。

**可复制Prompt**

```text
审查个人改密和管理员重置密码的完整调用链，包括旧接口。
确保成功后提升会话版本并注销该账号所有会话，旧令牌请求返回未认证。
检查密码类请求不会缓存到sessionStorage正文，也不会写入明文日志。
使用隔离账号测试两个并行会话，不修改现有测试人员密码。
如发现缺陷，给出触发条件、最小修复和回归结果。
```

**验收**：旧密码错误不能修改；成功改密后两份旧会话都不可使用；新密码可登录；新手机号成为普通账号登录名。

**常见问题**：只清当前浏览器的令牌，其他设备仍在线。修复必须覆盖服务端会话与数据库会话版本检查。

# 四 第三阶段 基础管理

## Step 5 工厂、产线、产品、物料和工序

**字段说明**

| 模块和表 | 主键 | 主要字段 |
| --- | --- | --- |
| 工厂 metal_factory | factory_id，自增BIGINT | factory_name、area、address、introduction、version、del_flag |
| 产线 metal_production_line | production_line_id，自增BIGINT | production_line_code、production_line_name、factory_id、version |
| 产品 metal_product | product_id，自增BIGINT | product_code、product_name、product_category、specification、dimensions、volume、purity、theoretical_weight |
| 物料 metal_material | material_id，自增BIGINT | material_code、material_name、material_type、specification；当前接口模型主要使用code、materialType、specification |
| 工序 metal_process | process_id，自增BIGINT | process_name、process_type、description、version |
| 产品工序 metal_product_process | product_id与sequence_no组合 | process_id、theoretical_loss |
| 产线产品 metal_line_product | 产线ID与产品ID组合 | 可生产产品关系 |

工厂面积为DECIMAL(14,4)，单位万平方米。重量和损耗等精确值主要为DECIMAL(20,6)，Java使用BigDecimal。产品dimensions使用JSON表达不同类别的尺寸。

产品、物料、工序是共享目录，不能默认每张表都有factory_id。基础物料档案也不是原材料库存；新增档案不会直接增加库存。

**可复制Prompt**

```text
在现有基础管理实现上检查字段、校验、版本控制和关联删除限制。
产品需维护有顺序的工序及每件理论损耗，产线关联可生产的产品。
编辑提交继续使用真实主键和version，列表连续编号只负责展示。
回显标签文字左对齐，红色*独立占位，文字不换行。
不要新增BOM、修改既有业务字段含义或重做共享目录的工厂归属。
先列出涉及文件和发现的差异，再实施明确需要的修改。
```

**验收**：并发编辑不会静默覆盖；已引用基础资料不能被删除破坏；工序顺序和理论损耗正确保存；界面编号变化不影响真实记录关联。

**常见问题**：把行号作为删除ID，或把单条工序的损耗当成所有产品共用的理论值。应使用真实主键，并在产品工序关联上保存理论损耗。

# 五 第四阶段 报价

## Step 6 类别公式、报价配置与保存快照

**实现说明**

metal_quote_rule保存base_price、pi_value和version。QuoteRuleService调用VolumeCalculator计算体积，现有逻辑为“体积×基础系数=单价，单价×数量=总价”。公式与尺寸单位要按类别核对，不能擅自把几何体积当作重量。

metal_saved_quotation保存quote_id、quote_no、request_id、request_hash、request_actor、factory_id、item_snapshot、total_price、rule_version、create_time等。其中quote_id为BIGINT自增主键，request_id为UUID幂等键，item_snapshot为JSON。

当前可计算类别包括铱坩埚平底、铱环、铱杆实心和铱杆空心，不能假定所有产品类别都支持公式。空心杆现有公式与常见圆环柱公式不同，需要单独确认业务口径后再改，不应由Codex自行替换。

**可复制Prompt**

```text
检查报价计算、保存和下载调用链。
沿用QuoteRuleService和VolumeCalculator，不重新设计几何公式。
保存请求由服务端读取当前配置计算，保存明细快照、规则版本和真实工厂归属。
重复request_id不得新增报价，重复请求内容不一致应拒绝。
下载使用实际保存快照，产品或规则以后变化不能修改历史报价。
为越权、重复提交、下载快照一致性添加有意义的验证。
```

**验收**：报价可以查到对应保存记录；下载内容等于保存快照；相同请求不重复创建；审计日志关联正确工厂和报价单号。

**常见问题**：下载时用当前规则重算，历史价格随配置变化；或审计归属直接采用客户端factory_id。两者都应从可信服务端状态或已保存记录取值。

# 六 第五阶段 生产工单

## Step 7 工单模型、编号和计划快照

| 表 | 主键 | 主要字段 |

| metal_work_order | work_order_id | order_no、customer、factory_id、production_line_id、owner_id、order_date、status、version |

**可复制Prompt**

```text
维护工单新增与编辑流程，沿用现有表和编号预留机制。
打开添加页面就显示唯一只读工单号，不显示“保存后自动生成”。
创建时保存产品和工序理论损耗快照，后续基础资料修改不回写历史工单。
通过真实主键关联产品明细，数量为正整数，工序计划开始早于结束。
检查幂等、并发编号和允许编辑的状态，不改变已进入生产工单的历史内容。
```

**验收**：同时打开两份新增表单得到不同编号；取消表单可产生号码空档但不得复用冲突；保存重试不重复创建；旧工单理论值不会随产品配置变化。

## Step 8 审核与生产状态

```text
PENDING待审核 → APPROVED审核通过待领料 → 真实领料 → IN_PROGRESS进行中
      ↓ 驳回                                               ↓ 满足全部完成条件
REJECTED → 修改后重新提交                                COMPLETED
```

**可复制Prompt**

```text
检查工单审核状态机以及仓储事件驱动的状态变化。
审核通过不能直接变为进行中，首次真实生产领料才触发进行中。
所有产品明细和工序满足完成数量且无未结算批次后，才能完成工单。
审核操作成功后显示“已操作”，按钮占位与未操作行对齐。
不要只根据按钮是否点过判断后台状态，检查状态与审核历史的一致性。
```

**验收**：重复审核不会重复推进；无权限审核被拒绝；领料后状态真实变化；只完成部分产品不会把整张工单标成完成。

# 七 第六阶段 仓储与库存

## Step 9 分清库存、单据和流水

| 数据 | 表 | 主要字段及含义 |
| --- | --- | --- |
| 库存余额 | metal_inventory | inventory_id、category、factory_id、warehouse_id、reference_id、batch_no、net_weight、quantity、version |
| 仓储主单 | metal_warehouse_order | order_id、order_no、kind、type、work_order_id、batch_id、factory_id、warehouse_id、status |
| 仓储明细 | metal_warehouse_order_line | line_id、order_id、inventory_id、reference_id、net_weight、quantity、物料信息快照 |
| 库存流水 | metal_stock_ledger | ledger_id、inventory_id、order_id、line_id、delta_weight、delta_quantity、balance_weight、balance_quantity、reversal_of |

库存有RAW原材料、SEMI半成品、FINISHED成品三类。原料重点计量重量，半成品与成品还涉及数量和来源批次。“单位名称”不是计量单位“件”。

**可复制Prompt**

```text
检查库存列表、仓储添加明细、详情与模板是否按类别分别呈现字段。
原材料要有物料编码、品名类别、规格、毛重、杂质、净重。
成品/半成品要有物料编码、单位名称、批次号、品名类别、规格、纯度、数量。
“字段要存在”不等于全部改成必填；保持已确认的必填规则。
毛重、杂质、实测净重做数字与精度校验，数量按正整数规则处理。
只修改缺失字段与展示，不擅自增加库存状态或改变余额计算。
```

**验收**：添加、导入、回显、详情对同一类别字段一致；模板不是空文件；只读人员无操作按钮和选择框；原料界面不会被成品数量字段误导。

## Step 10 出入还库、并发与库存调整

| 类型 | 方向 | 含义 |
| --- | --- | --- |
| RAW_IN | 入 | 原材料入库 |
| SEMI_IN / FINISHED_IN | 入 | 半成品/成品入库，生产来源时绑定任务及产出关联 |
| PRODUCTION_OUT | 出 | 生产领料，进入加工损耗链条 |
| PRODUCT_OUT | 出 | 成品对外出库 |
| EXCHANGE_OUT | 出 | 界面名“还料出库”，退给客户，不参与生产损耗 |
| SEMI_OUT | 出 | 半成品对外出库 |
| RAW_RETURN | 还库 | 生产余料还库，关联原领料 |
| PRODUCT_RETURN | 还库 | 成品退还，关联原产品出库 |

**可复制Prompt**

```text
检查仓储保存事务：主单、明细、库存和流水必须一起成功或回滚。
重复提交不能重复扣库，并发扣同一库存不能超扣。
原料还库和成品退还累计数量重量不能超过对应原出库范围。
库存调整通过调整单和流水登记，要求原因及权限，不直接覆盖余额字段。
已生效单据用冲销保留历史，有下游业务时检查依赖，不能简单DELETE。
测试只用隔离数据，不清理现有库存，不直接UPDATE业务余额。
```

**验收**：并发、重复请求和事务中途失败后，余额与流水仍一致；原料还库是库存增加，退客户的还料出库是库存减少。

**常见问题**：把库存编辑当成普通资料编辑，直接修改net_weight；或发生错误后只回滚主单，没有回滚流水。库存修改必须能追溯原因、来源与余额变化。

# 八 第七阶段 自动批次、报工与预警

## Step 11 自动批次关联

metal_process_batch仍保留在数据库中，虽然前端已取消独立批次页面与手工批次选择。核心字段是batch_id、batch_no、work_order_id、item_id、process_id、planned_quantity、completed_quantity、status、version。

批次号由工单号、时间、产品编号组合，并配合唯一约束和冲突处理。单靠时间字符串不能脱离数据库约束承诺并发唯一。

**可复制Prompt**

```text
检查自动加工批次机制，不恢复独立批次菜单或手工选择框。
同一工单、产品明细、工序的领料和产出绑定同一个未结算批次。
结算后再次领料才生成新批次，批次号由工单号+时间+产品编号组成。
必须校验当前工序可用数量、前序完成量与来源半成品。
累计产出保存时就不能超过计划数量，不要等到结算才报错。
检查并发重复领料是否会产生两个不应存在的OPEN批次。
```

**验收**：同批多次业务关联一致；不同产品明细不混批；前序未完成不能凭总工单数量跨序领料；并发唯一性有服务端保障。

## Step 12 损耗、报工与严格超出预警

```text
损耗 = 生产领料净重 − 原料还库净重 − 半成品产出净重 − 成品产出净重
平均损耗 = 损耗 ÷ 实际完成数量
异常条件：平均损耗 > 工单工序快照中的理论损耗
```

实际结算中，LossCalculator的returned参数是原料还库与产品产出回收重量的合计，不只是余料重量。当前新业务容差为0，不使用独立预警规则。

相关表：metal_work_report保存结算结果；metal_report_material保存物料损耗分摊；metal_warning_record保存预警；metal_warning_history保存处理历史。

**可复制Prompt**

```text
核对WarehouseService结算与LossCalculator。
理论值只取创建工单时保存的工序快照，不取产品当前配置。
严格大于才异常，相等正常；用未舍入值判断，避免显示精度影响预警。
产出数量合计应等于实际完成数量，回收重量不能超过领料。
汇总平均值用总损耗/总数量，不平均各批平均值。
验证结算重试、源业务冲销及预警处理不会篡改历史损耗。
```

**可手算验收**：领料100g，余料还库10g，半成品80g，完成5件，损耗10g、平均2g/件。理论2时正常，理论1.9时异常。结算后产出数量、报工和预警应引用同一批次。

**常见问题**：只减余料、不减产品重量，把所有加工产出都算成损耗；平均值先舍入导致临界误判；处理预警后把损耗状态直接改成正常。

**可复制Prompt**

审计对象与工厂范围从服务端实际记录提取，不信任客户端工厂字段。

**可复制Prompt**

核对数据看板每个指标的SQL来源、工厂范围、日期区间和有效状态。
金额使用已保存报价，损耗与数量按业务有效记录汇总。
页面按当前窗口合理布局，常用分辨率下完整显示。
不要用CSS隐藏溢出内容来制造“无需滚动”，不要写死演示数字。
提供指标口径、只读抽样核对和浏览器检查结果。

## 2 用完整任务描述减少来回修正

推荐结构：背景、现象、预期、范围、不能改变的规则、验收。举例：

```text
页面：/metal/warehouse-order，生产出库添加弹窗。

验收：普通字段与必填字段文字起点一致，无遮挡；提供截图或浏览器验证。
```

涉及流程时，加一组输入输出数字，比“优化逻辑”更容易验证。

## 3 不把所有任务都要求先给计划

按钮间距、文字替换等小改动可以直接实现并检查。库存算法、会话失效、权限和日志清理等跨模块修改，先看影响面和设计，再批准实现。明确“本轮只设计”或“按已确认设计实现”，避免对阶段目标理解不同。

## 4 约束业务范围，不机械限制文件数量

参考文章强调精确文件路径，这对定位很有帮助。但一次接口字段变化可能需要同时改请求模型、服务、前端与测试。可以说“先查这些入口，必要时修改关联文件并说明原因”，不要为了“只改一个文件”留下不一致的实现。

Codex可通过AGENTS.md读取项目约定，并支持目录层级规则。适合保存长期规则，细节设计另放文档并引用。规则应短、明确、可执行。[OpenAI官方AGENTS.md说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

## 6 用技能固化工作流，用MCP连接外部工具

# 十二 常见问题与修正Prompt速查

| 现象 | 需要检查什么 | 建议补充的约束 |
| --- | --- | --- |
| 页面编号与记录对不上 | 行号与数据库ID是否混用 | 展示连续编号，提交使用真实主键 |
| 库存出现重复扣减 | 幂等键、锁和事务 | 重复请求只生效一次，业务范围与请求内容校验 |
| 工单100件却无法加工100件 | 前序完成、当前可用量及未结算预留 | 给出可用量构成，不仅看工单总数量 |
| 报工全异常 | 回收口径、实际完成量、理论快照 | 把领料、余料、产出与损耗明细列出来手算 |
| 修改密码后旧设备还能访问 | auth_version和全部会话注销 | 测两个独立会话，而不是只测当前浏览器 |
| 菜单隐藏但接口可调用 | 后端授权和工厂范围 | 直接请求越权接口验证 |
| LAN页面报UUID或复制错误 | 非安全上下文兼容 | 在实际HTTP局域网地址验证 |
| 日志归档数量不足 | 展示截断被用于归档 | 完整集合脱敏，解压核验ID后才能删除 |
| 仓库只看到README | 当前分支与PR是否合并 | 报告远程分支和提交，不笼统说“已上传” |
| “测试通过”但仍复现 | 是否运行真实场景 | 报告命令、结果、覆盖边界及未验证项 |

# 十三 建议按这条小数据流程练习

1. 准备一座工厂、一条产线、一个产品、两道工序和一项基础物料。
2. 为产品配置每道工序理论损耗，创建小数量工单并审核。
3. 登记原材料入库，再生产领料；观察工单从待领料进入进行中。
4. 第一工序登记半成品产出及余料还库，确认数据齐全后结算。
5. 核对库存流水、批次关联、报工损耗和预警；相等与超出各准备一组隔离用例。
6. 第二工序领用合规来源半成品，登记最终成品产出并结算。
7. 确认工单完成条件，再做成品出库与受约束的退还测试。
8. 最后用日志追踪每个动作，并用另一工厂账号检查数据隔离。

实际练习需要你另外授权并选定隔离环境；本文生成没有写入这些业务记录。
