# 生产批次P0接口契约

- 日期：2026-11-12；版本：v1设计基线，尚无对应实现。
- 关联：[P0核对结论与数据模型](生产批次P0核对结论与数据模型-2026-11-12.md)、[开发任务计划](生产批次改造开发任务与阶段验收计划-2026-11-12.md)。
- 本文中的新URL、字段和错误标识都是待开发契约；明确列为“现有”的路径才是当前源码已有接口。
- 示例ID为占位的十进制字符串；不代表数据库中真实记录，不可直接对正式服务提交。

## 1. 领域身份与字段语义

| 字段 | 含义 | 不得混用 |
| --- | --- | --- |
| batchId | 本次加工/单据的目标生产批次 | 不是executionId或stockId |
| executionId | 一道工序的加工活动 | 不能跨工序复用为同一个加工记录 |
| stockId | 真实仓库库存明细 | 不充当UI唯一生产批次 |
| stockSliceId | stock下某批次的具体库存份额 | 同stock的A1、A2必须可分别选中 |
| sourceBatchId | 来源slice的生产身份，可为null | 不是目标batchId；服务端从slice读真实值 |
| orderStepId | 工单冻结路线节点ID | 不只比较processId或名称 |
| issueLineId、issueAllocationId | 原真实领料及来源份额 | 不因在制转移而编造新的原领料 |
| carryAllocationId | 当前execution承接该份原料责任的来源明细 | 不是通用退料授权，仍校验未加工可退余额 |
| operationId、requestId | 已提交生产操作及客户端幂等键 | 仓储/预占请求结果按各自域查询 |

## 2. 通用格式、精度和时间

- ID：JSON字符串，十进制正整数；ownerId允许"0"表示工厂。
- 净重：g，JSON字符串，最多两位小数；示例统一"300.00"，拒绝多余精度，不通过浮点误差静默舍入。
- quantity：PIECE阶段实际非负整数，写入消耗/结果一般要求正数；WEIGHT阶段对外null。现有持久化使用0并按measurementMode解释，由后端适配。
- plannedQuantity：整数或null，范围沿项目现有正整数及Integer.MAX_VALUE限制；不直接形成库存。
- referenceQuantity：仅适用计重成品等现有参考规则，不能替代实际quantity。
- version、sliceVersion、stockVersion、executionVersion：非负整数，不能省略需要更新对象的版本。
- reason：写入原因，拆合/撤销必填，最多500字符。
- requestId：UUID；同一操作重试沿用同请求与原请求体。改过分配内容就属于新意图，必须先核实旧结果，再使用新请求号。
- 时间：响应采用带时区ISO 8601，例如2026-11-12T10:00:00+08:00；业务日期沿现有YYYY-MM-DD。时区展示按Asia/Shanghai，不用日期作为并发依据。
- 客户端不得提交可任意改写的来源快照、债务归属、完成阶段或工厂权限。服务端读取冻结路线、实物来源与用户权限。

### 2.1 响应信封

复用AjaxResult：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "operationId": "8001",
    "requestId": "11111111-1111-4111-8111-111111111111",
    "committed": true,
    "affectedBatchIds": ["102", "103"]
  }
}
```

列表可沿现有TableDataInfo返回code/msg/rows/total；其他查询返回data。新批次列表规定使用TableDataInfo，避免调用方猜测两种分页形状。

所有写入响应的领域结果直接放在data下，与operationId/requestId/committed并列，例如拆分的source/results；不再额外包一层data.result。只有操作结果查询使用data.result保存原写入的data快照，并另外返回当前版本，避免把历史成功结果和当前余额混淆。

业务失败保持当前code/msg，新增稳定reasonCode及fieldErrors供交互定位。后端异常处理和前端request.ts必须一并保留这些字段；当前拦截器仅保证code与fieldErrors，不能假定reasonCode已自动透传。

```json
{
  "code": 409,
  "msg": "来源份额已变化，请刷新核对",
  "reasonCode": "VERSION_CONFLICT",
  "fieldErrors": [
    {"path": "sources[0].stockAllocations[0].sliceVersion", "message": "版本已变化"}
  ]
}
```

现有ServiceException通常返回JSON业务code，不保证HTTP状态也为409。新客户端必须兼容业务码及真实HTTP失败，不将两者混为一谈。旧退休拦截明确返回HTTP503。

### 2.2 错误分类

| code / reasonCode | 含义及恢复方式 |
| --- | --- |
| 400 / INVALID_ARGUMENT | 字段、精度、单位或组合不合法，修正输入 |
| 403 / FORBIDDEN | 权限不足，不以换工厂ID绕过 |
| 404 / NOT_FOUND | 对象不可见或不属于工厂，不泄漏他厂内容 |
| 409 / VERSION_CONFLICT | 版本变更，先核实原操作，再刷新上下文 |
| 409 / REQUEST_CONTENT_CHANGED | 同requestId内容不同，原结果先查询 |
| 409 / SOURCE_RESERVED | 来源有TEMP/BOUND占用，先依法释放/撤回 |
| 409 / PENDING_DOCUMENT_EXISTS | 相关草稿、待复验、退回等单据阻碍本次身份变化 |
| 409 / INVALID_STAGE | 阶段、路线或下道不兼容 |
| 409 / QUALITY_NOT_ELIGIBLE | 质量不允许或缺少可信资格依据 |
| 409 / ALLOCATION_NOT_BALANCED | 分配合计不守恒，不能留隐式残余 |
| 409 / WIP_ALLOCATION_UNRESOLVED | 在制、余料、损耗或材料来源无法确认 |
| 409 / SOURCE_INACTIVE | 来源已拆合退出或取消 |
| 409 / DOWNSTREAM_EXISTS | 已有有效下游，先逆序处理 |
| 409 / RETURN_SOURCE_NOT_ENTITLED | 当前责任无这份可退原料，不能仅凭原issue总余额退 |
| 409 / LEGACY_UNMAPPED | 历史身份未可靠映射，仅允许查询 |
| 500 / INTERNAL_ERROR | 结果可能未知，先查原请求；不能假定未生效 |

## 3. 新接口目录

所有路径在/metal下，均须登录、工厂隔离及对应业务权限。GET不创建批次、加工记录或占用；所有preview只计算，不写库。

| 方法 | 路径 | 输入/用途 | 主要响应 |
| --- | --- | --- | --- |
| GET | /production-batches/list | factoryId、orderId、orderItemId、lifecycle、pageNum、pageSize | rows/total；默认当前有效，可显式含历史 |
| GET | /production-batches/{id} | factoryId | 身份、计划量、明细阶段、库存/在制、可操作原因 |
| GET | /production-batches/{id}/context | factoryId、intent | 本次动作所需版本、份额、加工记录、来源、占用、阻断原因 |
| POST | /production-batches | 创建空生产身份 | batchId及version，不增加库存 |
| POST | /production-batches/{id}/executions | 开始首道或进入下一工序 | batchId不变、新executionId；尚未领料不产生INPUT |
| POST | /production-batches/splits/preview | 与拆分提交相同的业务分配，不要求requestId | 合计、差额、阶段、来源、是否可提交、fieldErrors |
| POST | /production-batches/splits | 拆分含计划拆分、库存拆分、部分完成带在制 | 操作、结果批次/份额、承接execution及版本 |
| POST | /production-batches/merges/preview | 来源参与量及分配依据 | 兼容性、剩余子批次预览、多stock结果 |
| POST | /production-batches/merges | 同阶段全量或部分合并 | 新batch、来源贡献、必要的剩余结果 |
| GET | /production-batches/{id}/trace | factoryId、direction=UPSTREAM/DOWNSTREAM/BOTH、pageSize、cursor | 批次节点/边、加工记录及明细引用、nextCursor |
| POST | /production-batches/{id}/complete | 批次生产完成 | COMPLETED及版本，不自动清欠料 |
| POST | /production-batches/{id}/cancel | 未执行空批次取消 | CANCELLED；不得有未处理单据或实际事件 |
| GET | /production-batches/operations/{requestId} | factoryId，当前操作者请求 | found/committed/operation/result及当前相关版本 |
| POST | /production-batches/operations/{operationId}/reverse | factoryId、requestId、reason、expected对象版本 | 反向操作结果，历史不删除 |

intent限定START_STAGE、SUPPLEMENT、SPLIT、MERGE、COMPLETE、REVERSE；只影响上下文展示，不作为客户端自授权限。追溯分页不得静默丢弃未返回分支，应给nextCursor和truncated标识。

沿用的现有接口：

| 现有路径 | 新语义/字段 |
| --- | --- |
| /production-order/{id}/flow、/report | 增加生产批次及加工明细、份额与拆合；原executions仍代表加工记录 |
| POST /production-order/executions/{id}/close | 仅结束本工序加工，校验batchId与execution版本，不直接完成生产批次 |
| /production-order/{id}/steps/{stepId}/complete、/{id}/complete | 工单工序与工单完工，统计包含有效移交前OUTPUT，不以父批次退出当完工 |
| /storage-orders/options | 增加batchId及intent；来源候选按stockSliceId返回 |
| /storage-orders/reservations及会话renew/release | 目标batch+execution及具体slice；保留原请求、版本和复验绑定规则 |
| /storage-orders及单据动作 | header目标batchId+executionId，line实际stockSliceId；具体行引用真实issue/carry |

首次领料可以由新UI先创建空批次、再创建加工记录、再进入原预占流程；任一步失败通过原请求查询恢复。空批次不产生实物，可按规则取消。第一版不再让新数据仅凭缺省executionId隐式创建另一份身份。

## 4. 查询模型

### 4.1 批次详情

```json
{
  "code": 200,
  "data": {
    "id": "101", "number": "PB-20261112-0001", "factoryId": "1",
    "orderId": "10", "orderItemId": "11", "lifecycle": "ACTIVE",
    "plannedQuantity": 100, "version": 3,
    "stageSummary": "工序一部分完成",
    "materialBalances": [
      {"kind": "STOCK", "stockSliceId": "9001", "completedStepIds": ["21"], "measurementMode": "PIECE", "quantity": 30, "netWeight": "300.00"},
      {"kind": "WIP", "executionId": "301", "processingStepId": "21", "completedStepIds": [], "measurementMode": "PIECE", "quantity": 70, "netWeight": "700.00"}
    ],
    "actions": [
      {"action": "START_STAGE", "allowed": false, "reasonCode": "INVALID_STAGE", "message": "整批尚未完成本工序，可拆出已完成部分"},
      {"action": "SPLIT", "allowed": true, "reasonCode": null, "message": null}
    ]
  }
}
```

这里只是结构示例。quantity=70必须有实际件数依据；如果只是计划剩余，改为quantity=null，另给plannedRemainingQuantity，不冒充真实在制件数。

### 4.2 具体库存候选

```json
{
  "stockId": "501", "stockSliceId": "9001", "sourceBatchId": "101",
  "sliceKind": "BATCH", "sliceVersion": 3, "stockVersion": 8,
  "warehouseId": "2", "measurementMode": "PIECE", "completedStepIds": ["21"],
  "balanceWeight": "300.00", "balanceQuantity": 30,
  "reservedWeight": "0.00", "reservedQuantity": 0,
  "availableWeight": "300.00", "availableQuantity": 30,
  "qualityEligibility": {"allowed": true, "basisRef": "quality-evidence-id"},
  "owners": [{"ownerId": "88", "availableWeight": "300.00", "availableQuantity": 30}]
}
```

quality-evidence-id是说明性引用，不是假定现有质量表已存在。实现必须映射真实质量/验收证据；不存在依据时不能默认allowed=true。

一个stock可能返回多个slice；一份slice也可以有多条owner分配。UI选项键用stockSliceId，sourceBatchId由服务端读取并作一致性核对。

### 4.3 拆分上下文

context响应除批次详情外，至少返回：

- executions：executionId、version、工序、人员、状态、真实input/output/return/recovery、carry及已确认损耗。
- stockSlices：实际份额、stockVersion/sliceVersion、OUTPUT引用、当前owner与材料来源贡献。
- wipSources：sourceAllocationId、executionId/version、可承接重量、实际件数口径、未加工可退量及原issue引用。
- pendingDocuments、activeReservations：仅当前有权查看的关联记录与阻断原因。
- quantityEvidence、allocationBases：哪些数量已确认，哪些方法允许使用；不能允许自由字符串绕过来源核实。
- actions及blockingReasons：机器标识和用户可读说明。

上下文与预览不锁定未来可用量；提交时在同一事务重查版本、占用、阶段及守恒。

## 5. 创建批次与进入工序

创建空批次：

```json
{
  "factoryId": "1", "requestId": "11111111-1111-4111-8111-111111111111",
  "orderId": "10", "orderItemId": "11", "orderVersion": 2,
  "plannedQuantity": 100
}
```

服务端生成编号和冻结路线引用；不接收客户端生产阶段或历史来源。首次创建计划不得无依据超过工单未分配目标；补产/目标调整单独明确，不通过重复新建隐藏超产。

开始工序：

```json
{
  "factoryId": "1", "requestId": "22222222-2222-4222-8222-222222222222",
  "batchVersion": 0, "intent": "START_STAGE",
  "orderStepId": "21", "processorId": "66"
}
```

首道与下道都使用START_STAGE；服务端按真实阶段判断允许的orderStepId。进入下道时batchId沿用，加工记录为新ID；不会仅因创建加工记录就增加实物。第一版一个可独立流转部分只有一个当前加工责任；部分并行必须先拆批。

SUPPLEMENT不调用此接口新建记录，而向现有OPEN execution制作真实生产领料单。SPLIT_TRANSFERRED记录拒绝补料、产出及退料。

## 6. 拆分契约

### 6.1 模式

| mode | 允许输入 | 约束 |
| --- | --- | --- |
| PLAN_SPLIT | 未实际开工的计划分配 | 无实际事件、库存、在制、占用或未处理单据；原空加工记录按规则取消，不生成实物 |
| STOCK_SPLIT | 已确认库存份额的分配 | 必须覆盖原批次本次整体退出需要处理的全部实物，不留隐式余额 |
| PARTIAL_COMPLETION_WITH_WIP | 已确认产出库存＋剩余在制 | 原记录移交终止，子记录承接在制；来源、余料、损耗须核清 |

多道加工历史可以保留；mode不能用来绕过真实存量范围检查。全批转出需覆盖当前所有有效余额，超出第一版支持组合时明确拒绝而非丢弃未处理余额。

### 6.2 已产30、在制70的提交示例

POST /metal/production-batches/splits

```json
{
  "factoryId": "1",
  "requestId": "33333333-3333-4333-8333-333333333333",
  "sourceBatchId": "101", "sourceBatchVersion": 3,
  "sourceExecutionId": "301", "sourceExecutionVersion": 5,
  "mode": "PARTIAL_COMPLETION_WITH_WIP",
  "reason": "已完成30件先进入下道，70件继续当前工序",
  "results": [
    {
      "clientKey": "finished30", "plannedQuantity": 30, "kind": "COMPLETED_STOCK",
      "stockAllocations": [
        {"stockId": "501", "stockVersion": 8, "stockSliceId": "9001", "sliceVersion": 3, "outputEventId": "401", "quantity": 30, "netWeight": "300.00", "allocationBasis": "CONFIRMED_BALANCE"}
      ]
    },
    {
      "clientKey": "remaining70", "plannedQuantity": 70, "kind": "WIP",
      "processorId": "66",
      "wipAllocations": [
        {"sourceAllocationId": "7001", "quantity": 70, "netWeight": "700.00", "allocationBasis": "CONFIRMED_BALANCE"}
      ]
    }
  ]
}
```

clientKey在一次请求内唯一，仅用于返回结果对应，不是正式批次编号。results.kind仅指定实物状态，不是创建不同批次类型。wipAllocations逐来源分配；例中一条700g来源只是简化样例，多来源必须逐项覆盖。

允许的allocationBasis基线为CONFIRMED_BALANCE、MEASURED；若采用账面比例，必须经具体规则确认后增加明确值及尾差规则，不能前端任填PROPORTIONAL就自动通过。MEASURED必须关联可审计measurementRef，不能只标一个枚举当作已称量。

计划也必须守恒：来源plannedQuantity非空时，所有结果的plannedQuantity合计等于来源，不能由实际产出倒推。来源没有生产计划（例如RETURN_RESIDUAL未分配目标）时，结果不自动创建新目标；计划转移须显式校验。

### 6.2.1 多料权、多来源份额的分配

上面的简化示例只在单一owner、单一来源且可由服务器唯一推导时允许省略内部构成。多owner或多来源时，每个结果的stockAllocations必须补充ownerAllocations和sourceAllocations，明确该结果承接什么，不能只给总件重让后端猜测。

```json
{
  "stockId": "501", "stockVersion": 8,
  "stockSliceId": "9001", "sliceVersion": 3,
  "quantity": 30, "netWeight": "300.00", "allocationBasis": "CONFIRMED_BALANCE",
  "ownerAllocations": [
    {"ownerId": "88", "quantity": 20, "netWeight": "200.00"},
    {"ownerId": "0", "quantity": 10, "netWeight": "100.00"}
  ],
  "sourceAllocations": [
    {"sourceAllocationId": "7101", "currentOwnerId": "88", "quantity": 20, "netWeight": "200.00"},
    {"sourceAllocationId": "7102", "currentOwnerId": "0", "quantity": 10, "netWeight": "100.00"}
  ]
}
```

- sourceAllocationId由context返回，指向该slice可用的确切来源；历史sourceOwner由服务端读取，不能用currentOwnerId覆盖它。
- ownerAllocations合计与sourceAllocations合计分别等于本结果总量，两轴不能相加为600g。
- sourceAllocations按currentOwnerId的合计必须匹配ownerAllocations；跨来源的全部结果分配不能超过原来源贡献，不能凭新增一个owner组合转移料权。
- preview必须逐结果展示两轴分配及依据；服务端校验当前owner、来源剩余、允许分配方法和全部合计，来源不清返回WIP_ALLOCATION_UNRESOLVED或ALLOCATION_NOT_BALANCED。
- 原slice持有多来源但本次是全量转移时，可由服务端完整承接全部明细并在预览显示；部分拆出若没有唯一且有依据的规则，必须提供具体分配，不能默认按30%/70%。
- PARTIAL_MERGE的来源stockAllocations同样适用此结构；在制来源按wipAllocations逐sourceAllocationId处理，必须同步可退原料责任，不用同一总量重复指派给多个结果。

### 6.3 响应示例

```json
{
  "code": 200, "msg": "拆分成功",
  "data": {
    "operationId": "8001", "requestId": "33333333-3333-4333-8333-333333333333", "committed": true,
    "source": {"batchId": "101", "version": 4, "lifecycle": "SPLIT"},
    "transferredExecution": {"executionId": "301", "version": 6, "status": "SPLIT_TRANSFERRED"},
    "results": [
      {"clientKey": "finished30", "batchId": "102", "version": 0, "plannedQuantity": 30, "completedStepIds": ["21"], "stockSlices": [{"stockId": "501", "stockSliceId": "9002", "sliceVersion": 0, "quantity": 30, "netWeight": "300.00"}]},
      {"clientKey": "remaining70", "batchId": "103", "version": 0, "plannedQuantity": 70, "executionId": "302", "executionVersion": 0, "completedStepIds": [], "carryInWeight": "700.00", "carryInQuantity": 70}
    ],
    "wipTransferIds": ["7501"]
  }
}
```

部分完成的30件必须已通过真实入库/交接确认且未被冲突下游消耗；700g必须是可证明在制，不把未确认损耗当余额转走。若70只是计划数，carryInQuantity=null并保留plannedQuantity=70。

### 6.4 服务端原子步骤

权限及工厂→同request结果检查→锁版本与实际来源→检查待办/占用→核实所有件数重量及来源分配→创建结果身份→库存份额转移→新execution和WIP_TRANSFER→原状态退出→写来源及幂等结果→提交。

任一步失败不留下半笔结果。preview也执行合法性计算，但不执行后半段写入。

## 7. 合并契约

POST /metal/production-batches/merges：

```json
{
  "factoryId": "1", "requestId": "44444444-4444-4444-8444-444444444444",
  "mode": "FULL_MERGE", "reason": "两批已完成工序二，合并进入工序三",
  "sources": [
    {"batchId": "102", "version": 4, "stockAllocations": [{"stockId": "601", "stockVersion": 2, "stockSliceId": "9101", "sliceVersion": 2, "quantity": 30, "netWeight": "290.00"}]},
    {"batchId": "103", "version": 4, "stockAllocations": [{"stockId": "602", "stockVersion": 2, "stockSliceId": "9102", "sliceVersion": 2, "quantity": 70, "netWeight": "680.00"}]}
  ]
}
```

示例重量是工序二实际产出，比工序一少的部分必须已有真实损耗或其他处置证据，合并本身不创建这些损耗。不得按30/70件反推重量。

服务端从来源读取工单产品组、路线、阶段、计划分配与质量，不接受客户端直接声明兼容。FULL_MERGE要求来源全部当前余额参加、无未完成在制；第一版不开放任意加工中WIP合并。

响应包括targetBatchId、目标多个stockSlices、sourceContributions、来源新版本和MERGED状态。B持有601、602两个真实stock下的份额，不能承诺单一stockId。

PARTIAL_MERGE时sources中填实际参与量，例如30件和70件中的20件。服务端预览必须同时返回：

- 合批结果B50的来源及重量。
- 70件来源拆出的参与20件身份及剩余50件身份。
- 全量参与的30件来源退出，部分来源整体拆分退出，剩余量不留在已退出的原编号。
- 中间参与批次及所有操作边，便于完整追溯。

提交将必要拆分和合并同事务执行；remainingResults由服务端按确切余额计算，用户在预览核对，版本变化则重新预览。不能在客户端发送两次独立写入冒充原子合并。

计划量另行承接：FULL_MERGE继承来源已分配目标之和，实际数量不因此被补足；PARTIAL_MERGE对每个有计划的来源必须提交plannedQuantityForMerge，剩余目标为原计划减该值。目标分配必须有业务依据，不能默认按实际件数比例推算；预览同时显示计划与实物两个维度。该字段不直接新增工单目标。

## 8. 仓储、预占、复验与入库的扩展契约

沿用POST /metal/storage-orders/reservations。示例：

```json
{
  "factoryId": "1", "requestId": "55555555-5555-4555-8555-555555555555",
  "sessionId": "66666666-6666-4666-8666-666666666666", "reservationVersion": 0,
  "type": "PRODUCTION_OUT", "intent": "STAGE_ISSUE",
  "orderId": "10", "batchId": "102", "batchVersion": 0,
  "executionId": "303", "executionVersion": 0,
  "lines": [
    {
      "reservationLineId": "77777777-7777-4777-8777-777777777777",
      "warehouseId": "2", "stockId": "501", "stockVersion": 8,
      "stockSliceId": "9002", "sliceVersion": 0, "sourceBatchId": "102",
      "netWeight": "300.00", "quantity": 30,
      "allocations": [{"ownerId": "88", "weight": "300.00", "quantity": 30}]
    }
  ]
}
```

intent=STAGE_ISSUE或SUPPLEMENT，两者都指向已确定的加工记录，不在预占里暗换工序。batchVersion和executionVersion来自实际创建后的响应，示例0只说明字段类型。

预占响应保留原sessionId/version/status/expiresAt/lines，增加核实后的batchId、executionId、各slice引用。绑定单据、复验和过账仍检查会话版本及实际明细；实际发出与实收及差异承担沿用当前规则。

关键要求：

1. batchId是目标，sourceBatchId是来源，可相同（同批进入下道）或在既定承接规则下不同；来源以slice为准。
2. 未绑定普通原料sourceBatchId=null，不能被当成已完成前工序半成品。
3. 同stock不同slice用不同reservationLineId；一个行内owner合计等于该行实物，不能跨slice自动偷配。
4. 改目标批次、加工记录或来源时，释放旧占用并重新核对；已有BOUND会话遵循撤回/退回流程。
5. 创建/修改单据header必须带batchId和executionId，并与预占上下文一致。
6. 生产入库的目标batch和execution一致；完成阶段由冻结工序和真实验收推导，不能从客户端completedStepIds照抄。
7. 所有出入库、移库、调整、料权动作同步份额分区；不只改生产领料而漏掉其他扣减入口。

## 9. 原样退料和移交授权

真实退料仍走/storage-orders单据及复验，不新增绕仓储的“直接退余额”接口。明细增加：

```json
{
  "issueLineId": "451", "issueAllocationId": "460",
  "stockId": "490", "sourceStockSliceId": "8901",
  "carryAllocationId": "7601", "netWeight": "20.00", "quantity": null
}
```

单据header中的executionId是当前E2，而issue属于原E0。服务端验证有效承接路径、当前可退未加工份额及原issue未退总量；不能因为executionId不同一概拒绝，也不能仅凭carryAllocationId放行所有原料。

普通未绑定原料返回UNASSIGNED；生产来源实物若原批次已退出，按模型文档创建RETURN_RESIDUAL结果，保持原实物阶段。响应返回returnedStockSlices及必要的createdResidualBatches，不复活父批次，不直接归入后道生产阶段。

RETURN_RESIDUAL与真实仓储退料同事务创建，不能退料成功但身份失败；反向处理也检查结果是否已被下游使用。

## 10. 结束工序、批次完成、撤销

### 10.1 结束工序

POST /metal/production-order/executions/{id}/close：保留factoryId、requestId、version、physicalChecked、reason；新增batchId一致性字段。

仅普通OPEN加工记录走结束逻辑。可支配重量需计carry；未明确处置的在制不能无依据全部记损耗。SPLIT_TRANSFERRED不能再次close，移交操作已完成其终止。

### 10.2 完成生产批次

POST /metal/production-batches/{id}/complete：factoryId、requestId、version、reason。服务端核验必需工序、实际成品、未处理单据、在制及异常处置，不自动产生出入库或清债。

工单完工仍使用原工单接口，按有效加工事实与目标核对。报废2件后合98件不能正常完成100件目标。

### 10.3 拆合撤销

POST /metal/production-batches/operations/{operationId}/reverse：

```json
{
  "factoryId": "1", "requestId": "88888888-8888-4888-8888-888888888888",
  "reason": "误拆且尚未发生下游操作",
  "expectedBatches": [{"batchId": "102", "version": 0}, {"batchId": "103", "version": 0}],
  "expectedExecutions": [{"executionId": "302", "version": 0}]
}
```

服务端读取原操作完整影响范围，不能因为请求少填对象就跳过检查。目标已领料、产出、退料、交付、再拆合或有冲突待办时拒绝；先逆序处理。允许撤销时恢复原身份/责任、反向份额与转移，保留原INPUT/OUTPUT及反向操作，不删历史。

## 11. 幂等、未知结果与事务

1. 新生产动作复用现有production_execution_operation的factory+actor+requestId唯一性；hash包含动作、目标及规范化业务体，同键不同意图拒绝。
2. 操作结果与业务变更同事务持久化；初次成功及重复请求均返回原提交结果，另给current对象版本用于刷新，不能把旧快照误当当前可用余额。
3. GET /production-batches/operations/{requestId}仅查询当前操作者有权请求；成功时found=true、committed=true及原result；未查到时code=200、data.found=false、committed=false。
4. found=false只表示当前未看到已提交结果，不证明并发中的原请求永远不会提交。网络超时后只可继续查或重放同一请求，不换新键重复做。
5. 不在数据库事务外先写一条虚假成功/失败状态，不为同步流程引入额外异步任务队列。
6. 锁定、校验、来源转出、结果建立、份额/在制移动、审计和结果同事务；跨工厂请求拒绝。
7. 预览没有预留保证；真正提交必须重查其他预占和关联版本。纯拆合存在有效来源占用时先拒绝，不偷偷消耗已有会话。
8. 仓储请求结果仍查/storage-orders/operations，预占结果仍查/storage-orders/reservations/operations，不能拿生产请求号查错操作域。

## 12. 权限与兼容策略

### 12.1 权限

- 查询复用metal:work-order:list/query及实际库存可见范围。
- 开始工序等复用metal:work-order:execute，并继续检查本工厂有效人员及领料复验能力。
- 拆合/撤销推荐在P1明确新增metal:production-batch:transform、metal:production-batch:reverse权限；同时受工厂及相关实物管理权限制。P0不写入菜单权限表、不默认所有加工人员拥有此权。
- 库存预占、仓储创建、复验继续原对应权限。管理员绕过普通菜单权限也不能绕过工厂、来源和守恒。

### 12.2 旧接口兼容

| 情况 | 处理基线 |
| --- | --- |
| 退休旧前缀 | 维持HTTP503，不为新模型解除全局退休拦截 |
| 当前execution查询与新工单流程 | 保留加工记录ID，新增batch关联，不全局重命名 |
| 新模型生产写入 | 要求明确batchId、executionId及来源slice；不允许缺字段时另建孤立execution |
| 已可靠映射的历史单据 | 通过服务器映射读取；需编辑/重新占用时补足明确身份与份额，不能仅按工单猜测 |
| 未映射历史 | 可只读；写入返回LEGACY_UNMAPPED，不按同工单全部归并 |
| 老前端缺少新字段 | 新模型切换后明确拒绝并提示刷新升级，不静默退回旧建批语义 |

新旧程序并跑期间若未接入份额写入，禁止旧程序修改已切换工单。实际切换方案在P5演练，不能靠前端隐藏按钮维持账实一致。
