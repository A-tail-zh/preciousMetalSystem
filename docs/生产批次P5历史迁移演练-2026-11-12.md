# 生产批次 P5 历史迁移演练

日期：2026-11-12。对应开发任务计划 DB-04、DB-05、BE-11；沿用 P4 生产批次模型及 V81～84，不新增 DDL。

## 范围与规则

工具为 `tools/production-batch-p5-history-migration.mjs`，Java 实现 `tools/ProductionBatchP5HistoryMigration.java`，真实数据库断言检查为 `tools/ProductionBatchP5HistoryMigrationCheck.java`。使用 business-flow-check 和 ponytail 规则，以最小受控空记录映射验证来源不猜测、历史不改账、事务与幂等。

本期工具只接受 `127.0.0.1:3323/production_batch_p5_20261112_<10hex>`，拒绝前端专用 `762c61d418` 库；不支持正式库 apply。凭据从私有环境文件载入，不进入命令行或报告。

`scan` 在只读 SERIALIZABLE 事务中扫描指定工厂所有 `batch_id IS NULL` 的 execution，输出可复核 manifest 与哈希。存在以下任一情况只列歧义：非空来源、非零重量/数量/金额、事件、任何状态（包括冲销/删除）的单据、库存来源、占用、在制或欠料引用；不按当前余额零推断历史从未发生。引用覆盖 execution/source_execution、order/work_order/origin_order、order_item、origin_step；同订单的可疑业务引用也保守阻止自动映射。另列退休 `metal_process_batch*`、`metal_warehouse_common*`、`metal_batch_wip_balance` 表行数，必须人工复核，不将它们迁成第二套批次。

候选仅完全空的首道 OPEN 或完全空的 CANCELLED，要求完整有效订单、产品快照及连续未关闭冻结路线；计划为有效正整数，先对同产品组所有非取消未映射记录与既有活动 PB 整体核算计划容量；超目标时全部活动候选列歧义，不按 execution ID 先到先得。同产品组任何非取消记录存在歧义，也阻止空 OPEN 候选映射；空 CANCELLED 仍可只读映射。完全空但不能证明计划的重量记录也留人工审核。每 execution 创建一个独立 `origin_action=MIGRATION` 的 PB，完成步骤为 `[]`；CANCELLED 对应 CANCELLED 生命周期。不会虚构前序完成，不新增生产、仓储或债务业务流水。

`apply` 必须显式传 schema、factory、actor、UUID requestId、manifest 文件及其哈希。锁定工厂后核对原请求审计；相同请求同哈希返回原结果，内容变化拒绝。新请求重新扫描比对完整 manifest、execution 版本和 NULL 关联，在同一事务中分配现有 PB 编号、建立批次及关联、写技术映射审计；任何错误回滚。生产批号复用现有 `ProductionBatchService.nextNumber()`，只调整包级可见性。

## 隔离执行

先运行 `node tools/prepare-production-batch-p5-isolation.mjs` 创建全新空 schema。设置 `P5_MIGRATION_ENV_FILE` 为该 schema 的 `test-env.private.json`，扫描命令格式：

```text
node tools/production-batch-p5-history-migration.mjs scan <schema> <factory> <manifest.json>
node tools/production-batch-p5-history-migration.mjs apply <schema> <factory> <manifest.json> <actor> <UUID> <scanManifestHash>
node tools/production-batch-p5-history-migration.mjs check-old-program <schema> <factory> <manifest.json>
```

扫描 manifest 包含内部业务明细，应保留在私有 `.runtime` 目录。本工具依赖已有 P4 编译依赖清单与当前 metal 编译产物，输出独立 `migration-build`，不覆盖 P4 或 P5 核心测试目录。

## 真实数据库证据

独立 schema 和结果以 `.runtime/production-batch-p5-20261112/migration-flyway-proof.json`、`migration-mapping-proof.json` 为准；日志同目录 `migration-flyway.log`、`migration-mapping.log`。

Flyway 12.4.0 从空库迁移至 V80，插入合成旧生产加工、产出事件、单据和 300.00 重量/30 件库存料权样本，再迁 V81～84，validate 通过，重跑迁移数为零。按旧列逐行比较库存、料权、库存流水、execution、execution_event、单据六张表，保持一致；新增来源/分配/血缘不自动生成，carry 默认零。初次演练停在 V80 的库及一次末尾测试断言失败库保留，未删除或倒回；最终完整结果使用另一个全新 schema，避免将失败后的续跑冒充全流程。

受控映射样本包含：有事件和库存的旧记录一条（保持歧义）；同产品组空首道 OPEN 和空 CANCELLED 各一条（独立两个 PB）。断言覆盖 dry-run 不写、过期 manifest 拒绝、首条映射后注入故障完整回滚、相同请求重复结果一致、旧复杂记录保持 NULLbatch、业务账表逐行不变、完成步骤无虚构。补充同产品组仅有余额但没有事件/单据的歧义兄弟，验证空 OPEN 也被阻止；两条空 OPEN 各计划20/目标30，验证两条均歧义。

完整 mysqldump 恢复证据由主验收提供：`.runtime/production-batch-p5-20261112/backup-restore-proof.json`。从合成 HTTP schema 导出完整库并恢复到另一个新空随机 schema，22 张业务表逐行相同；源库导出前后相同，目标 Flyway V84。私有 dump 不进入文档。

## 冻结点与回退边界

正式切换必须先冻结生产、仓储、在制、占用和欠料相关写入口，记录所有未审单据与歧义清单，保存可恢复完整备份及余额快照；只对已核实来源运行受控方案，再复核余额、映射与历史查询，最后开放写入。

`check-old-program` 检测已有新 PB 即拒绝宣称直接回旧程序安全，保留新数据。新批次、份额、来源分配或拆合产生后，旧程序不能理解其责任边界。失败恢复应停止写入、保留现场，使用已验证冻结点备份恢复到独立环境并核对；冻结后新增业务需单独核实处置，不能通过删新批次或删新流水恢复。

未执行正式库扫描、真实业务来源裁定、正式 apply 或服务切换。合成样本通过不替代正式全量演练与人工歧义处理。
