# 从贵金属项目提炼的 Codex 精准提示词方法

用途：下次构建其他项目时，把一句模糊想法转成Codex能够实现和验证的任务。贵金属加工系统用于举例，方法可迁移到电商、预约、报销、设备管理等项目。下文模板是建议的工作方式，不是对生成质量或开发耗时的保证。

# 一 精准提示词的核心

精准不等于写得长，也不等于列出很多框架名称。它要让开发者知道：为谁解决什么问题，什么条件下可以做什么，哪些东西必须保持，以及怎样证明完成。

可以按六项组织：

```text
目标：本轮最终要得到什么行为或交付物。
背景：项目阶段、角色、现有技术或资料。
业务规则：关联关系、状态、公式、权限及例外。
范围：本轮做哪些；哪些留到以后。
验收：输入、操作、预期输出，以及失败边界。
交付：需要代码、文档、测试、截图还是提交记录。
```

小改动用两三句即可；新项目与跨模块业务需要补全关键条件。官方建议明确目标、上下文、约束和完成条件；本文的六项结构是在此基础上结合本项目提炼的实践模板。[OpenAI官方最佳实践](https://learn.chatgpt.com/guides/best-practices)

# 二 从本项目看 什么信息容易漏

| 本项目经历的表达问题 | 更精准的表达 | 新项目中的迁移方法 |
| --- | --- | --- |
| “这些字段是必要的”后来澄清为字段要有 | 字段必须展示，哪些必填另列 | 分清字段存在、可编辑、必填、自动生成 |
| “还料”与“还库”混淆 | 退客户减少库存；生产余料还仓增加库存 | 给业务名写来源、去向及数据影响 |
| “按理论损耗预警” | 实际平均损耗严格大于工单快照才预警，相等正常 | 写比较单位、运算符、阈值来源和版本 |
| “批次号唯一” | 组合规则加数据库唯一约束和冲突处理 | 定义并发与重试，不能只给字符串格式 |
| “隐藏加工批次” | 隐藏页面与手工选择，保留后台自动关联 | 明确隐藏界面、停用功能、删除数据的区别 |
| “没有权限不显示” | 菜单、按钮、选择框隐藏，接口仍需拒绝越权 | UI权限与服务端授权分开验收 |
| “库存可以编辑” | 余额调整生成调整单与流水，不直接覆盖历史余额 | 先分清档案修改与业务交易 |
| “工单100件怎么不能做100件” | 当前工序受前序完成量、已加工量及预留量约束 | 写实际可用量，不只写总计划 |
| “改密后重新登录” | 该账号全部会话失效，包括其他设备 | 说清作用对象和范围 |
| “提交GitHub” | 推送指定分支、创建PR，是否合并另说明 | 区分本地保存、提交、推送和发布 |

这些例子提示：先消除业务歧义，再决定文件名和代码结构。给出几十个字段但没有状态与例外，仍可能生成逻辑不完整的系统。

# 三 新项目开始前 准备一页需求

不需要先懂数据库设计。先回答下面的问题，不知道的写“待讨论”，不要让模型把猜测当成已确认需求。

1. 谁使用？例如总部管理员、门店管理员、普通用户。
2. 最重要的一条流程是什么？从哪个动作开始，到什么结果结束？
3. 管什么对象？订单、资源、库存、人员、预约等。
4. 对象之间是什么关系？一个订单能否含多个明细？一个用户能否属于多个组织？
5. 有哪些状态？谁能从哪个状态改到哪个状态？
6. 什么行为会改变金额、数量、余额或资源占用？
7. 谁能看哪些数据？按本人、部门、门店还是全量？
8. 历史配置变化后，旧业务按旧值还是新值？
9. 取消、失败、重复点击、并发请求怎样处理？
10. 第一版必须做什么？支付、短信、导出、移动端等是否属于本期？

本项目对应：工厂是隔离范围，工单包含产品明细，产品明细有工序，仓储事件改变库存，结算产生损耗与预警。其他项目应重新确认自己的对象与规则，不能原样照搬这些表名。

# 四 第一步 让Codex帮你整理需求

直接复制下面的“提示词生成器”，填入你的自然语言想法：

```text
我准备构建一个新项目，希望你先作为需求分析与开发协作者，帮我把想法整理成可执行提示词。

项目想法：<用自己的话描述>
用户角色：<知道的先写，不清楚写待讨论>
核心流程：<例如提交预约→确认→到店→完成，或写目前想到的流程>
技术要求：<已有偏好；不确定则请给简单合适的建议并解释>
运行环境：<Windows/Linux、本地或部署环境>
第一版范围：<必须做的功能>
暂不实现：<可选，例如真实支付、短信、多语言>

先不要写代码。
请输出：
1. 业务术语表、核心对象关系、状态流转、角色权限和数据范围。
2. 会改变实现的关键歧义，给出可选方案及建议。
3. 将已确认规则与暂定假设明确分开。
4. 按依赖顺序拆成可独立验收的开发阶段。
5. 每阶段给出可直接发给Codex的Prompt及验收例子。
不要编造我的业务规则，也不要为了“完整”加入大量未要求的功能。
```

你负责判断业务是否符合实际；Codex负责把表达补成结构化设计。不要在业务口径尚未确定时一次批准所有阶段。

# 五 第二步 用一个完整例子补齐规则

本项目预警的模糊Prompt：

```text
做损耗预警，超了就报警。
```

改进版：

```text
实现加工结算时的损耗判断。
领料100g，余料退回10g，产品产出80g，完成5件时，损耗10g、平均2g/件。
理论值取创建工单时保存的工序快照，不随产品后来修改。
实际平均值严格大于理论值才生成预警，相等正常。
比较使用未舍入值，显示保留精度不能改变判定。
本轮只实现站内预警记录，不加短信或邮件。
验收：理论2时正常，理论1.9时异常；重复结算不能产生重复有效报工。
```

迁移到预约项目，可写：

```text
预约一个容量为1的会议室，开始时间必须早于结束时间。
占用区间采用左闭右开：[开始,结束)，因此10:00结束与10:00开始允许相邻。
只有已确认预约占用资源，取消后释放资源。
两个用户并发提交同一时段，只能一人成功，另一人得到明确冲突提示。
同一请求重试不能创建两条预约。
本轮不做周期预约、收费和短信。
验收：重叠被拒绝、相邻允许、取消可重约、并发只有一个成功。
```

这里的会议室规则是新项目的示范假设，需要你的业务确认。可迁移的是“数值例子、边界、状态、并发、范围”的表达方式。

# 六 第三步 分阶段构建 每次交付一条能运行的链路

| 阶段 | 应交付什么 | 不足以验收的结果 |
| --- | --- | --- |
| 需求与设计 | 术语、关系、权限、状态、关键例子 | 只有功能名清单 |
| 项目骨架 | 前后端可启动、基础接口可调用、配置示例 | 只有目录和空文件 |
| 身份与权限 | 登录、退出、授权与隔离可验证 | 只有登录页面 |
| 一条核心业务 | 表单→接口→事务→数据库→回显完整闭环 | 只有CRUD接口 |
| 异常与历史 | 并发、幂等、取消、失败回滚与快照 | 只验证成功提交 |
| 日志与运维 | 能定位故障，关键操作可追溯 | 输出一大段无关联日志 |
| 验收与部署 | 测试证据、构建、部署及回滚说明 | 只说“开发完成” |

例如本项目先打通一条“领料→产出→还库→结算→预警”小数据流程，再扩展批量导入和统计，比先完成所有列表但无法结算更容易发现模型与规则问题。

不是所有项目都需要Redis、JWT、队列或微服务。让Codex根据并发、部署和团队约束解释选择，不要因为本项目用了就要求新项目全部照搬。

## 骨架阶段Prompt

```text
按已确认设计初始化项目，只完成可运行骨架。
技术栈：<已确认选择>；部署环境：<环境>。
提供前后端目录、依赖锁定文件、环境变量示例、健康检查和启动说明。
秘密只通过环境注入，示例不含真实凭据。
数据库采用可追踪迁移，不在启动时任意删除重建已有数据。
本轮不实现完整业务。
验收：从新目录按说明安装依赖后能够启动并调用健康检查；报告实际命令和结果。
```

## 单模块实现Prompt

```text
目标：实现<模块>的<具体行为>，依据<设计文档与章节>。
上下文：<已有目录、接口、模型或相关页面>。
规则：<权限、状态、关联、精度、历史与例外>。
范围：<本轮做什么>，暂不实现<明确排除项>。
沿用已有架构；必要的跨层修改可以进行，但不要无关重构。
验收：<正常例子>、<失败例子>、<边界或并发例子>。
交付：代码、必要迁移、相关测试、启动或操作说明；报告实际验证结果。
```

不熟悉代码时不用强行指定文件。可让Codex先根据仓库选择入口；已有项目时提供真实路径能加快定位，但“只许改一个文件”不应阻止必要的前后端一致修改。

# 七 数据规则 怎样写才不会变成普通CRUD

字段清单之外，为重要字段说明六件事：含义、类型单位、来源、是否必填、谁能修改、历史如何保留。

以本项目为例：

| 信息 | 明确写法 |
| --- | --- |
| 主键 | 数据库内部唯一标识；页面行号不能用于更新删除 |
| 单据号 | 打开新增页面预留，只读、唯一，允许取消造成空号 |
| 理论损耗 | 每件克数，非负，创建工单时复制为历史快照 |
| 净重 | 克，精确十进制，按业务验证范围和小数位 |
| 库存余额 | 由单据和流水变化，不允许绕过业务直接覆盖 |
| version | 防止旧页面覆盖别人修改，不是单据编号 |

对任何新项目，都建议让Codex回答：

```text
针对核心对象，请补充字段字典和约束。
区分内部ID、展示编号、业务编号与请求幂等键。
标出金额/重量/时间的单位和精度、服务端生成字段、唯一范围及历史快照字段。
列出不能仅用普通增删改查实现的规则，并说明验证层与事务边界。
不确定的业务定义列为待确认，不能自行定稿。
```

# 八 修改页面 怎样用最少的话说清楚

模糊：把页面调整一下，跟图片一样。

精准：

```text
页面：<路由或操作入口>。
当前问题：<具体不一致>。
参考图：<附图>，只参考<布局/间距/颜色中的指定内容>。
预期：<可观察的效果>。
保持：字段、校验、权限、请求及业务逻辑不变。
验证：在<窗口大小>下检查，不靠裁切内容制造布局正确。
```

本项目的“跳过红色*，文字左对齐”可以明确成：“*独立占位，标签文字起点一致、不换行；仅改标签样式”。新项目也可套用，避免模型顺手改掉必填逻辑。

# 九 排查Bug 怎样提供证据

```text
环境：<浏览器、部署方式、访问地址类型>。
账号角色：<角色即可，不提供密码令牌>。
复现：1.<动作> 2.<输入> 3.<结果>。
预期：<正确行为>。
实际：<错误文字、截图、脱敏响应或traceId>。
近期变化：<网络、配置、依赖或代码修改>。
请追踪调用链，找到原因后做最小修复。
不要无关重构；添加能复现该问题的必要回归验证。
报告根因、修改、实际测试与未验证范围。
```

本项目的局域网问题说明，“localhost能用、HTTP局域网不能用”本身就是重要证据。直接说“页面坏了”容易导致模型从错误方向排查。

# 十 用验收控制结果 而不是反复说认真一点

“详细检查、不要有Bug、代码质量要高”无法定义完成条件。把它们换成行为：

- 权限：A组织用户请求B组织详情，服务端应拒绝或不可见。
- 幂等：同一请求重复发送两次，只创建一条业务记录。
- 原子性：中途写入失败，主记录、明细与余额全部回滚。
- 历史：修改当前配置，已保存业务结果不变化。
- 边界：等于阈值正常，严格超过才异常。
- 取消：执行取消后资源释放；存在下游依赖时按规则拒绝。

这些不是所有项目都必须实现的功能清单。先判断它是否涉及钱、库存、资源占用、权限或历史记录，再选择适用的验收条件。

# 十一 让规则在下一次任务仍然可用

长期规则放项目AGENTS.md：目录、常用命令、核心约束、完成条件。具体业务设计另放文档，不要塞进所有聊天和所有提示词。不要依赖“我以前说过”保证新对话准确恢复。

通用建议内容：

```md
# 项目协作约定

- 阅读本次任务相关设计和现有实现，区分确认规则与假设。
- 沿用现有架构，不因单次任务做无关重构。
- 涉及权限时同时验证界面和后端授权。
- 涉及金额、余额或资源占用时检查精度、并发、幂等及事务。
- 不输出真实凭据；不擅自删除数据、修改历史或公开发布。
- 执行与变更匹配的测试，报告实际结果和未覆盖范围。
- 业务口径有变化时更新相关设计与验收文档。
```

命令要按新项目实际情况填写，不能将本项目npm脚本复制给没有这些脚本的工程。AGENTS.md示例是候选内容，本次没有创建实际规则文件。

# 十二 你下次可以直接发送的总提示词

```text
我想开发<项目名称>，请先帮助我形成准确的需求与分阶段开发Prompt。

背景：<谁使用、为什么需要>。
核心流程：<用自己的话描述一条从开始到结束的流程>。
角色与数据范围：<谁能操作什么、能看到哪些组织或个人的数据>。
关键对象：<已知的实体及关系，不确定处标注待讨论>。
关键规则：<状态、公式、单位、限制和例外>。
历史要求：<配置修改是否影响旧业务，能否删除或取消>。
技术与环境：<已有选择或请你建议>。
首版范围：<必须完成>。
暂不包含：<明确排除>。

本轮先不写代码。
先给术语、对象关系、状态流转和权限矩阵，找出影响实现的关键问题。
把确认事实与建议分开，不为我自动决定业务。
然后按依赖顺序输出可验收阶段；每阶段包含目标、上下文、规则、范围、验收和交付。
每个重要业务给一个正常例子和一个失败或边界例子。
最后给我首个阶段可直接复制执行的Prompt。
```

拿到设计后，不要只看技术名词，重点看三件事：你的业务能否完整走通，失败时数据是否仍正确，验收例子能否由你手工判断。确认后再逐阶段实施。

本文提炼的关键经验是：把项目里的“工单、库存、批次”换成新项目里的对象，同时保留对含义、状态、权限、历史、失败与验收的明确表达。精准Prompt来自清晰业务定义和及时反馈，不需要一次写出完美的长篇指令。
