## 2. 业务规则与撤销模型

### 2.1 撤销单位

撤销针对一次完整 `SPLIT` 或 `MERGE` 操作，不是任意删除其中一条来源边。部分合并所产生的中间批次和剩余批次也纳入同一影响范围。撤销新增 `REVERSE_TRANSFORM` 操作，`reversal_of` 指向原操作；原操作结果和来源边不改写、不删除。

恢复原来源批次生命周期，取消本次产生的结果批次；恢复原加工记录的状态、关闭原因、关闭时间和已确认损耗，取消本次生成的承接加工记录。所有受影响对象版本递增，不能把旧版本号复原。

### 2.2 保存什么

新拆合操作在写入前保存来源批次和加工记录状态，以及材料来源剩余数量、重量、可退数量和可退重量；提交后将完整影响范围写入操作结果的 `reversalSnapshot`。

| 数据 | 用途 |
| --- | --- |
| `reversalSnapshot.before.batches` | 原批次ID、生命周期 |
| `reversalSnapshot.before.executions` | 原加工记录ID、状态、关闭原因/时间、损耗 |
| `reversalSnapshot.materialBefore` | 来源ID及原剩余/可退余额，防止恢复时扩大责任或退料额度 |
| `reversalSnapshot.batches/executions` | 完整影响范围，包括中间和结果对象 |
| 材料分配 `IDENTITY_TRANSFER/WIP_TRANSFER` | 按原贡献顺序的逆序恢复来源、份额、料权分区和在制责任 |
| 材料分配 `REVERSAL` | 本次补偿留痕，关联撤销操作 |

金额/重量以精确十进制保存；跨端ID沿用字符串。取消后的承接来源保留但余额归零，不能再次使用。恢复可退额度以原快照为准，不以当前总重量推算。内部身份转移和撤销均不产生虚构 INPUT、OUTPUT、入库、借料或还料事件。

### 2.3 必须阻断的情况

- 无完整撤销快照的历史操作、重复撤销、跨工厂或无权限请求。
- 有未撤销的后续拆合、退料承接、新的非取消加工记录，或承接记录已有有效补料/产出/退料等事件。
- 有有效预占，或草稿、待复验、退回的关联仓储单据。
- 结果库存已被下游领用、发货等使用，材料贡献或料权已经不满足原始逆向恢复条件。
- 批次或加工记录状态已变化、影响范围版本缺失/重复/过期，或工单已结束/删除。

预检查返回 `allowed` 和 `blockingReasons`，提交时在事务和工厂锁内重新检查，不能把预检查当成写入许可。补偿模拟先通过，才实际写入；任何中途异常整体回滚。

### 2.4 下游逆序与空加工取消

先撤销后续拆合或仓储使用，再处理上游拆合。后续操作已经被合法补偿时，不因历史边仍存在而永久阻断；预检查返回当前版本，支持“先撤子操作，再撤父操作”。

例如结果批次进入下一工序并领料后，先按原仓储复验流程冲销领料。若加工记录仍 OPEN、有效事件及所有投入/产出/承接余额均为零，且无未处理单据，可取消这条空加工记录，然后撤销上游拆合。取消只忽略已完全冲销事件和已过账的补偿单，不删除历史。流程中的 `started` 仍表示曾有历史，旧编辑入口仍按全部历史保护，不能借完全冲销改写旧加工人员或计划。

已经实际生产并关闭的工序不会被通用拆合撤销自动重新打开；必须先具备合法的下游补偿路径。P4没有增加跨已结算工序的任意重开能力。

### 2.5 幂等、权限和并发

新增权限 `metal:production-batch:reverse`；查询追溯使用 `metal:work-order:query`。操作结果查询允许执行权限或撤销权限，但仍限当前工厂、当前操作者、当前请求号。

UUID请求号与工厂、操作者、请求指纹关联；相同请求及内容返回已提交结果，相同请求号改变内容拒绝。两个并发撤销只允许一个补偿提交。工厂锁和完整版本集合同时保护，不靠前端按钮限制。

## 3. 100件拆30和70再合并

真实MySQL回归保留并复跑 P3 主链，覆盖“先产30、剩余70在制”，并非仅开工前拆计划。

| 步骤 | 批次与实际行为 | 必须成立 |
| --- | --- | --- |
| 1 | A计划100，实际领料生产，先确认30件产出 | 100是目标，只有30是已确认产出 |
| 2 | 将A拆成已完成的A30和在制A70 | A30继承30的已验收来源；A70承接70的在制及来源责任；原INPUT/OUTPUT不复制 |
| 3 | A30沿用自身PB进入下一工序；A70继续原工序 | 两者可独立排产、领用和关闭，互不继承对方进度 |
| 4 | A70完成后沿用其PB进入下一工序，两者到达相同阶段 | 计划、实际件数、重量、来源、料权分别核对；不能跨不兼容阶段合并 |
| 5 | 合并A30与A70为B100 | B有30/70贡献，旧身份停止使用；库存总量和料权守恒，不新增生产或欠料 |
| 6 | B继续末工序并确认100件成品入库 | 实际有效OUTPUT合计100，不能把A、A30、A70、B计划累计为300 |
| 7 | 从B向上查A30/A70/A，从A向下查B及仓储去向 | 原始领料、承接、各阶段事件、实际入库/发货及补偿都有依据 |

撤销示例：B尚未被下游使用时，撤合并恢复A30/A70，再按依赖允许撤前序拆分。若B已发货，直接撤合并拒绝，先合法冲销发货，再重新获取完整版本检查。存在实际关闭生产的情况不会通过“撤销拆合”抹掉生产。

额外验证：30+70部分合并为50，明确保留另50；逆向恢复中间身份和库存贡献。实际损耗2件时只合并98，原目标100仍保留，正常完工不得按计划或缓存伪造100。

## 4. 接口契约增量

基础路径 `/metal/production-batches`，沿用项目 `code/msg/data` 返回结构。

| 方法与路径 | 请求 | 结果与约束 |
| --- | --- | --- |
| GET `/{id}/trace` | `factoryId`、`direction=BOTH/UPSTREAM/DOWNSTREAM`、`pageSize=1..100`、`cursor` | 节点、来源边、加工记录、贡献分配、生产/仓储事件、单据、库存份额、材料来源、操作及下一页标记 |
| GET `/operations/{operationId}/reverse-context` | `factoryId` | `allowed`、`blockingReasons`、`expectedBatches`、`expectedExecutions` |
| POST `/operations/{operationId}/reverse` | 工厂、请求号、原因、完整影响版本 | 新撤销操作ID、原操作ID、受影响批次ID及 `committed=true` |
| GET `/operations/{requestId}` | `factoryId` | 原请求结果恢复；撤销专用权限人员也能查询本人请求 |

撤销请求示意，ID及版本必须取本次实时预检查结果，不能只提交当前页面批次：

```json
{
  "factoryId": "9001",
  "requestId": "6ce450a3-7063-41e2-a2c4-4801791cc9ec",
  "reason": "下游使用已撤销，恢复原批次责任",
  "expectedBatches": [
    {"batchId": "4", "version": 2},
    {"batchId": "5", "version": 1},
    {"batchId": "6", "version": 1}
  ],
  "expectedExecutions": []
}
```

只接受已定义请求字段，原因必填，幂等内容发生变化拒绝。统一结构化 `reasonCode` 及完整错误信封仍未全量迁移，本期以 `code/msg` 和 `blockingReasons` 为实际契约。

追溯按工厂和订单产品项隔离，不加载整个工厂数据。边按游标分页，反向和正向遍历均保留分支；单页事实可能重叠，前端按ID去重。撤销后的原始边仍返回，并标记已撤销。超过10000条候选边显式409，不静默截断。查询使用只读事务，不触发建批、来源回填、库存计算写回。
