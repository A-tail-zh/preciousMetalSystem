# 生产批次P2实现与隔离数据库验收

日期：2026-11-12。范围：P2“不拆合的跨工序闭环”。本文件记录当前代码与实际验证结果，不代表正式部署或P3拆分、合并验收。

## 1. 交付结论

已接通统一生产批次、库存份额、份额内料权、仓储预占及审核复验。同一生产批次可以逐道建立加工记录，编号保持不变；仓储领料引用加工记录，并从服务端派生生产批次身份。首道领普通原料，后续工序领同批上一道产出。

验证结果：154项不同的后端定向测试通过，其中18项使用真实隔离MySQL；10项Playwright前端测试通过（8项浏览器交互、2项纯函数）；后端打包、前端类型检查和生产构建通过。真实Flyway从V81升级至V82、校验及重复运行通过。

验证分层必须区分：MySQL测试直接调用真实服务和事务；浏览器测试拦截全部业务API。未启动真实隔离HTTP应用做浏览器端到端联调，因此任务计划中“前端接真实隔离后端”的整体QA-01验收仍需补充。不得把上述两层测试描述成浏览器真实后端全链路验收。

正式业务数据库、正式服务和历史业务数据均未写入。保留工作区已有改动；未提交、推送或切换服务。

## 3. 数据模型

迁移文件：`backend/ruoyi-admin/src/main/resources/db/migration/V82__production_batch_storage_slices.sql`。沿用P1的`metal_production_batch`及加工记录`batch_id`，不引入第二种生产批次。

| 表/字段 | 本阶段含义与约束 |
| --- | --- |
| `metal_storage_stock` | 原物理库存主账，仍是唯一实物总量；不复制库存行来表示生产批次 |
| `metal_storage_batch_slice` | 库存内份额：factory、stock、可空batch、weight、quantity、version；`BATCH`必须有batch，`UNASSIGNED`必须无batch |
| `batch_key` | 由`COALESCE(batch_id,0)`生成；同工厂、库存、批次唯一，包括无批次份额 |
| `metal_storage_batch_slice_owner` | 份额内料权余额；以份额、owner为键，owner=0沿用工厂料权语义 |
| `metal_storage_batch_slice_entry` | 与真实仓储事件关联的份额及料权增减审计，保存原因；用于逆向恢复 |
| `metal_storage_event.stock_slice_id` | 本次真实事件操作的份额，可空以兼容历史事件 |
| `metal_storage_issue_allocation.stock_slice_id` | 领料实际扣用的份额，与料权分配一起追溯 |
| `metal_storage_reservation.stock_slice_id` | 预占落到实际份额及owner；与stock、factory复合外键约束 |
| `metal_storage_document.batch_id` | 单据头生产批次，由加工记录派生，审核使用该权威身份 |

重量沿用`DECIMAL(20,2)`，件数`BIGINT`，数量与版本非负。复合外键限制跨工厂、跨库存引用。

三项守恒同时成立：

1. 同库存各份额重量、件数之和等于物理库存。
2. 每份额各owner余额之和等于该份额实物余额。
3. 同库存同owner在全部份额中的余额之和等于原料权主账。

份额只是原实物与料权的分区，不是新增入库，不新增外部投入或欠料。计划件数也不直接生成实物。

### 3.1 存量处理

V82在持久DDL之前，先用临时表CHECK断言检查原库存与料权余额及孤儿记录；不平衡直接失败，不自动修账。通过后，将全部存量库存和料权镜像为`UNASSIGNED`。

不推测历史生产批次，不改原库存、料权、单据明细的既有列，不伪造历史份额流水。新增可空列使旧记录保留原意；历史无批次加工记录继续用于历史业务，但不能消费新批次专属份额。

MySQL DDL存在自动提交边界；预检能阻挡已知数据问题，不能保证任何中途DDL异常都自动回滚。正式升级前仍需备份、冻结写入和演练；本次没有执行正式升级。

## 4. 业务规则及服务改造

### 4.1 库存、料权与来源

`StorageBatchSliceService`统一处理份额解析、实际归属、版本、owner余额、预占保护、守恒检查和份额流水。`StorageLedgerService`在原事务内接入收货、领料、提料、原样退料、料权归还、调整和冲销。

冲销依据原事件的份额流水逆向恢复，避免重复执行普通镜像逻辑；历史无份额事件只在唯一可确定份额时兼容，遇到歧义拒绝。退料追溯原领料及实际份额；退出的来源批次不能通过退料重新激活。

库存查询仍返回物理stock行，附加`stockSlices`，页面内部展开份额以供选择。服务器保存继承领料的来源快照，产出/回收来源固定；后续退料不能改写旧产出的来源组成。`ProductionSourceBalances.remaining()`提供剩余可用来源，避免反复跨工序将内部流转累计成外部新投入。

当前P2同一产出stock内来源组成一致。P3若在同一stock下拆出不同来源组成的份额，必须补充精确的份额级来源贡献分配；不能直接复用stock级来源比例完成差异来源拆合。

### 4.2 预占与审核复验

`StorageReservationService`从加工记录读取工单、批次；传入批次与实际不符即拒绝。关联新批次的库存行必须显式带实际份额与版本，不能仅凭物理库存ID让服务端猜选。

预占按物理库存、物理料权、份额实物、份额料权四层余额校验，并跨多行汇总需求，防止同一份额被多行重复超用。历史无份额预占保守计入占用，不因新增分区而漏算。

建单绑定预占；审核核对实际stock、slice、owner与绑定内容，在同一事务内复验余额并记账。已绑定单据不再沿用编辑时的旧版本号盲目拒绝：另一张合法单据先通过后，仍按当前余额和原绑定快照审核。身份或额度不符仍拒绝；失败保留原待审单据及占用状态。

余额、来源和占用的可变读取采用当前锁定读，防止事务等待工厂锁后继续使用旧RR快照。RAW_IN故障注入测试确认物理库存、料权、份额、事件、单据、审核任务和操作记录共同回滚；该测试没有预占。审核失败后BOUND占用保持由独立的超额审核测试验证。

### 4.3 同批跨工序

`ProductionBatchService`冻结有序工序节点ID，重复工艺也按不同节点识别。开始下一道要求前一道加工记录已结束、可承接库存完整、无冲突待审单据/预占及其它阶段正余额。PIECE阶段还要求计划件数全部产出并验收；WEIGHT阶段按确认重量与前道原入库库存完整性检查，不将重量换算成实际件数。

首道只消费允许的普通`UNASSIGNED`原料；后道只消费同一生产批次、实际上一节点的份额。补料继续使用当前加工记录，不另建记录；进入下一道才创建新的加工记录。

旧接口不能再隐式创建新孤立加工记录；原成功操作仍可幂等重放，历史无批次记录保留兼容。工序结束不等于生产批次完工；生产批次完工也不等于工单完工或欠料结清。关联单据过账及加工记录结束/取消会推进批次版本。

## 5. 接口与前端接入

| 接口 | P2行为 |
| --- | --- |
| `GET /metal/production-batches/list`、`GET /{id}` | 统一批次列表、详情及关联加工记录 |
| `GET /metal/production-batches/{id}/context?intent=START_STAGE\|SUPPLEMENT\|COMPLETE` | 返回对应操作上下文、份额和可执行性原因 |
| `POST /metal/production-batches/{id}/executions` | `requestId`、`batchVersion`、`intent=START_STAGE`、`orderStepId`、`processorId`；服务端检查实际顺序 |
| `POST /metal/production-batches/{id}/complete` | `requestId`、`version`、`reason`；独立执行批次完工并记录幂等结果 |
| `GET /metal/production-batches/operations/{requestId}` | 已提交返回`found=true`及result；未知返回`found=false, committed=false` |
| `GET /metal/storage-orders/options` | 可传factoryId、executionId、type、sessionId、batchId；校验记录与批次一致并过滤可用来源 |
| `POST /metal/storage-orders/reservations` | 既有预占协议增加批次及实际份额，响应返回服务端派生的batchId |
| 仓储建单、编辑、审核 | 单据头存实际batchId，明细存实际stockSliceId；审核不相信客户端伪造的生产身份 |

实际URL按控制器前缀拼接；表中`/{id}`用于对应批次路径。ID沿用字符串传输，重量使用十进制文本。新批次库存行保留`stockId`，增加`stockSliceId`、`sliceVersion`、`stockVersion`、`sourceBatchId`；owner分配仍在既有`allocations`中。

前端在工单流程加入`ProductionBatchPanel.vue`，可创建批次、进入工序、查看上下文及批次完工。仓储表单改为选择“工序加工记录”，展示批次号/工序/人员/记录ID；从工单明确建批后再领料。结束加工按钮改为“结束本工序”，避免与批次完工混淆。

`LineEditor.vue`按实际份额选择，汇总分组不跨来源批次；CSV导入增加份额引用并验证。预占传递批次身份。操作结果查询`found=false`保持未知/等待状态及原requestId，不误判为已完成，也不换新请求盲重试。

P0完整结构化`reasonCode/fieldErrors`错误封装尚未全部落实；当前仍使用既有业务code/msg，操作上下文提供原因。调用方不能假定完整P0错误协议已经实现。

## 6. 100件跨三道工序的实际验证

真实MySQL测试`ProductionBatchP2MysqlTest`主链覆盖：

1. 创建生产批次A，计划100件，建立第一道加工记录E1。
2. 普通原料预占→草稿→提交→审核→领料；单据、预占与实际份额对应。
3. 第一道入库100件，形成属于A、来源节点一的库存份额；结束E1。
4. A进入第二道生成E2，批次ID和编号不变；预占并领用第一道A份额，产出100件，结束E2。
5. A进入第三道生成E3，仍沿用A；领第二道A份额，产出最终100件并结束E3。
6. 三道加工合计6条实际INPUT/OUTPUT生产事件；内部承接不再次增加外部材料债务。
7. 独立完成生产批次并重放相同请求，再完成工单；材料ADVANCE欠料仍为1000，不因完工被自动核销。

每一步检查库存、料权、份额及来源守恒。另有阶段测试明确拒绝“计划100、仅产30”整批提前下道。将30独立下道、70继续在制及后续合并，必须在P3实现真实拆分/承接，当前没有开放这个入口。
