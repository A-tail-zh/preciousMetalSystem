# 工单管理详细设计（已批准实施）

## 依据与范围
以需求（部分）.md第9节四张截图为依据，继承1442px基准、247px侧栏、82px顶栏、统一比例及既有蓝橙红色。MasterGo未能直接读取属性，截图为本次原型依据。
本期：工单CRUD、多产品工序计划、审核通过/驳回/重新提交、工厂隔离、版本冲突、快照与关联保护。仓储领料回料和自动报工不在本期，不使用模拟记录。

## 列表与表单
列表：选择框、工单号、客户、工厂名称、产线名称、负责人、状态、创建人、创建时间、标题。末列表头按图保留“标题”，按钮查看、操作、编辑、删除。顶部添加/编辑/删除，编辑仅可编辑单选亮起，删除选中全部可删除时亮起。16条分页、创建顺序升序，新建到末页。无搜索、导出或报价列。
表单：单据编号（新增保存后自动生成）、客户、工厂、产线、开单日期、负责人、添加产品区。补充工厂/产线选择是已批准的原型差异。客户必填100字符；日期必填默认当天；工厂、产线及本厂有效负责人必填。普通用户固定本厂。
每张单1～100明细，同产品允许多明细，数量1～1000000整数。产品必须由产线关联且配置工序。工序名称顺序只读，每道开始/结束必填，分钟精度，开始早于结束；下一工序不得早于前一工序结束，可相接。不检查跨产品/跨工单冲突，不限制开单与计划先后。
工厂/产线改变确认后清空依赖明细，产品改变重载工艺及清空计划。下拉同宽限高可滚动并重开回顶。取消/确认，失败保留输入。

## 详情
返回入口、基本信息、左报工表右产品Tab/工序表。基本信息：单据编号、产品类型、数量、工厂、产线、日期、负责人、状态、创建人、时间。类别去重、数量合计；Tab产品名+明细序号+数量。工序表仅名称/开始/结束，计划/实际切换；实际为空显示—及未接入提示。报工表真实空状态，无虚假查看编辑按钮。

## 状态与权限
PENDING待审核；REJECTED驳回（原因必填，最多500）；APPROVED审核通过待领料；IN_PROGRESS进行中。
新建即待审核，编辑待审核/驳回不改状态；待审核可通过或驳回；驳回显式重新提交。通过后不能编辑、删除、撤回；后续真实领料才可触发进行中，本期无手动开工。
权限metal:work-order:list/query/add/edit/remove/approve/reject/resubmit。普通人员本厂、管理员全厂；具有审核权限者可自审，审计记录真实人员。本期批量删除最多100，任一失败整批拒绝。详情、选项、写入、状态操作均检查范围。

## 数据与API
V6（实施前确认V1～V5已成功）：metal_work_order主表、metal_work_order_item明细、metal_work_order_step计划和实际、metal_work_order_review历史、metal_work_order_sequence日流水。
工单号WOyyyyMMddNNNNNN，上海时区，成功保存分配，不复用删除号。UUID创建请求幂等，原请求同内容返回原ID，不允许不同内容覆盖。ID/小数接口字符串、version整数。日期yyyy-MM-dd，时间yyyy-MM-dd HH:mm:ss，秒00。损耗g/DECIMAL(20,6)，尺寸快照cm。
/metal/work-order提供GET list/详情、POST新建、PUT修改、DELETE批量；POST /{id}/approve,reject,resubmit携带version。options工厂/产线/负责人/产线产品/工艺。创建请求customer,factoryId,productionLineId,ownerId,orderDate,requestId,items；明细id（旧明细）、productId,quantity,plans(processId,startTime,endTime)。状态/编号/快照/审计不由客户端赋值。
产品/工序保存资料快照；旧明细同产品编辑保留快照，新明细/改产品取当前配置。工厂、产线、人员显示名保留快照。逻辑删除保留明细和审核历史。

## 事务与关联
整单、明细、计划、历史整体事务；固定工厂→产线→产品→工序→负责人→工单锁顺序，关联检查使用锁定当前读。状态修改及保存使用版本。
有效工单阻止产线解除工厂/跨厂转移/移除被使用产品，阻止工厂、产品、工序删除。产线物理删除检查含逻辑删除工单的历史引用。原工厂接口也受相同约束。人员后续改名/停用/转厂不改历史快照；重新提交、通过时负责人须仍有效同厂。

## 验收
真实CRUD、重启保留、两厂权限、原型布局和分页；并发编号/幂等、完整计划回显及非法计划拒绝；旧快照不变；引用限制；批量原子性/版本冲突；驳回重提及通过锁定；无虚假领料报工。回归已有基础管理和计算。已批准在feature/work-order分支实施并完成验证后提交Git。

补充实现说明：依赖记录在工单行之前加锁，避免基础资料删除与工单编辑形成反向锁等待。事务使用READ_COMMITTED并在锁定后重验关系。长表单只滚动弹窗正文，头部和底部操作保持可访问。

## 请求示例

```json
{
  "requestId": "12345678-1234-1234-1234-123456789012",
  "version": 0,
  "customer": "客户名称",
  "factoryId": "1",
  "productionLineId": "1",
  "ownerId": "2",
  "orderDate": "2026-10-13",
  "items": [
    {
      "productId": "1",
      "quantity": 5,
      "plans": [
        {
          "processId": "1",
          "startTime": "2026-10-14 09:00:00",
          "endTime": "2026-10-14 10:00:00"
        }
      ]
    }
  ]
}
```

编辑另带id及原明细id；审核提交 `{ "version": 0 }`，驳回另带reason。产品类型、名称、规格、尺寸、净重与工序损耗均由后端快照生成，不能通过请求设置实际起止。验证与截图见verification.md及work-order-live-verification.json、work-order-restart-verification.json。

## 实际时间口径调整（2026-10-13，用户确认）

本节替代此前计划/实际双时间方案。新增、编辑填写实际开始、结束时间，详情只展示实际时间，移除切换控件。顺序、必填和分钟精度校验保持。为兼容接口，items.plans[].startTime/endTime字段仍沿用名称，语义为实际时间；后端仅写入actual_start_time/actual_end_time，返回值亦取实际字段。人工录入不自动触发领料、报工或状态变化。

V7把旧计划归档至metal_work_order_legacy_plan并保留原记录，历史计划不回填实际时间。旧工单实际时间显示—；待审核/驳回工单须编辑补充实际时间后才能通过或重新提交；已通过工单保持锁定。迁移递增版本，拒绝旧页面覆盖。V6不修改。

## 2026-10-13最终调整：仅计划时间

用户确认实际时间不需要。本次使用V8，保留原计划；只有原计划为空时才把上阶段人工填写时间带入计划。新增编辑写入计划字段，详情仅显示计划时间，无计划/实际切换；审批仅检查计划时间，不再要求实际时间。已通过133项后端测试、13组真实接口及页面审核流程回归，前端构建成功。此说明替代上阶段实际时间方案。
