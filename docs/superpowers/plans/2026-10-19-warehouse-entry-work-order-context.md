# 仓储录入生产工单上下文权限修复计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans 按任务执行，先失败回归、再实现、再验证。保留现有未提交修改；本轮不提交或推送GitHub。

**Goal:** 只有仓储工单查看、添加权限的人员，能够选择本厂生产工单并加载产品、工序、客户，正常完成授权范围内的仓储录入，无需额外授予完整生产工单查询权限。

**Architecture:** 新增仓储录入专用的只读生产工单上下文接口，返回显式白名单字段，按仓储工单添加／导入授权并执行工厂和工单状态校验。前端替换工单选择、批次回显两处完整详情请求，沿用并补强现有异步上下文检查。完整工单详情接口及原保存校验保持原权限边界。

**Tech Stack:** Java/Spring Security/JdbcTemplate、Vue 3/TypeScript/Element Plus、JUnit/Mockito、Playwright/Chrome。

**Spec:** 本文“已确定的设计与边界”及用户已确认的权限缺口分析；本轮仅制定计划，未修改业务代码、数据或角色授权。

## 已确定的设计与边界

- 不向既有角色批量补授 `metal:work-order:query`，不放宽 `/metal/work-order/{id}`。
- 不通过隐藏生产工单选择框绕开问题；有仓储新增权限的人员应能完成该业务。
- 不修改业务表、数据库结构、库存计算、工单状态流转、8小时续期、历史数据或已有权限菜单。
- “本批次结算”仍需要独立的 `metal:process-batch:settle` 权限；仅仓储新增人员可以登记不结算单据，不因此获得结算权限。
- 仓储候选接口既有权限不扩大；仓库字典权限、库存新增权限、仅仓储查看权限不自动获得新上下文接口权限。
- 使用隔离工厂、角色、账号及业务数据验证，完成后清理；保留测试审计日志，不修改现有账号密码。

## 接口约定

新增 `GET /metal/warehouse/work-order-context?factoryId=...&workOrderId=...`。

授权条件：`metal:warehouse-order:add` 或 `metal:warehouse-order:import`；超级管理员沿用既有授权机制。Controller校验权限，Service沿用候选服务的权限防御及FactoryScope校验。

两个ID必填且为正整数。首先校验工厂访问范围，再在所选工厂范围内查询未删除工单；工单状态仅接受当前候选允许的 `WAITING_MATERIAL`、`IN_PROGRESS`。不存在／不属于所选工厂／已删除的工单不返回上下文，不暴露其他工厂详情；状态不适用明确提示刷新选择。

响应沿用 `{code:200,data:...}`，ID以字符串传输：

```json
{
  "workOrderId": "123",
  "factoryId": "10",
  "customer": "甲方公司",
  "items": [{
    "id": "456",
    "productId": "789",
    "snapshot": {"code": "PRD-001", "name": "产品名称"},
    "plans": [{"processId": "11", "processName": "工序名称", "sequenceNo": 1}]
  }]
}
```

产品明细和工序按工单已保存的顺序及快照返回；不重新拼装当前产品配置。仅返回工单自己的产品明细、工序；不返回审核记录、驳回原因、创建人、损耗配置或其他完整详情字段。不调用完整 `WorkOrderService.detail()` 后再删字段，避免新增字段意外泄露。
