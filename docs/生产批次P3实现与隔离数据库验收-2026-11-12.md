# 生产批次P3实现与隔离数据库验收

日期：2026-11-12。阶段：P3拆分、在制承接及合并。本文记录本轮代码、合成数据验证与实际边界；不代表正式上线或真实历史库迁移完成。

## 1. 交付范围

已实现同一种生产批次的计划拆分、库存拆分、部分产出与在制承接、全量合并及部分合并。同一结果批次继续跨工序使用原编号，合并结果生成新的生产批次编号。

主链已通过真实隔离MySQL服务事务验证：100件投入，先完成30件；拆出已完30件与在制70件；30件独立进入工序二，70件在原工序继续；两者完成工序二后合并为100件，进入工序三并产出100件成品。原历史投入、产出不复制，内部移交不增加库存或材料欠料。

最终后端定向验证为173项通过，其中25项使用真实MySQL，0失败、0错误、0跳过；前端模拟API测试16项通过（13项浏览器、3项纯函数）。后端打包及前端生产构建通过。另有2个真实HTTP浏览器场景通过：实际计划拆分提交及真实合并预览；合并预览前后22张业务表逐行完全不变。完整100件生产主链由真实MySQL服务测试完成，不宣称浏览器执行了全部加工。

本轮由多个子代理分别承担拆合与加工服务、来源与迁移、前端及交互测试；主代理负责仓储调用接入、真实数据库链路、真实HTTP应用及最终整合。

## 2. 业务规则与依赖

依据：[任务计划](生产批次改造开发任务与阶段验收计划-2026-11-12.md)、[P0模型](生产批次P0核对结论与数据模型-2026-11-12.md)、[P0契约](生产批次P0接口契约-2026-11-12.md)、[P2验收](生产批次P2实现与隔离数据库验收-2026-11-12.md)。历史文档保留原阶段事实，不回写成“过去已实现”。

1. 系统只保留一种生产批次。库存份额、加工记录、在制责任不是新增批次类型。
2. 原批次整体退出，所有继续使用的部分均有明确结果身份，不能在退出编号中留下隐式余量。
3. 拆合不记真实出入库，不复制INPUT/OUTPUT，不新增外部投入、借料或还料。工序产量仅来自真实有效OUTPUT。
4. 同stock的份额可以重新分配，物理stock及其owner总账保持不变。多stock合并后仍保留多个stock，不能伪造一个汇总stock。
5. 计划、实际件数、重量分别守恒。计划100、实际98不能被合并自动补为100实物，也不能把目标自动改成98。
6. 完成阶段来自冻结路线节点ID及真实验收，重复工艺按不同节点区分；不接受客户端任意声明完成阶段。
7. 合并要求同工单、产品组、冻结路线及共同完成阶段；不接受加工中的WIP合并。
8. 来源有草稿、退回、待审核单据或有效TEMP/BOUND占用时拒绝拆合，不偷偷迁移占用。
9. 来源、料权、件数或剩余在制无法确认时拒绝，不用默认比例猜测。当前只开放`CONFIRMED_BALANCE`，实测需先形成真实仓储/加工事实。
10. 提交校验工厂、权限、版本、幂等及全部分配；预览不保留余额且不得写库。失败整体回滚。

## 3. 数据结构及迁移

新增：`backend/ruoyi-admin/src/main/resources/db/migration/V83__production_batch_transform.sql`。不修改V81/V82，不清理或重写已有业务行。

| 对象 | 内容 |
| --- | --- |
| `production_batch.completed_step_ids` | 拆合结果继承的有序完成节点前缀；历史值保持NULL，不推测回填 |
| `production_execution.carry_in/out_weight/quantity` | 当前加工责任的移入、移出，与真实INPUT/OUTPUT分别保存 |
| `production_execution.status` | 增加`SPLIT_TRANSFERRED`移交终态；原OPEN/CLOSED/CANCELLED保留 |
| `metal_production_batch_edge` | 一对多、多对一来源边；记录操作、计划贡献、实际件重及依据；不作为产量 |
| `metal_production_material_source` | 份额或加工责任下的精确来源，保存初始贡献、当前余额、当前owner、历史sourceOwner/Kind、父来源及真实issue授权 |
| `metal_production_material_allocation` | 库存身份移动、WIP、领用、产出、退回、回收、损耗与反向分配审计，按用途关联仓储事件、生产操作或来源所属加工记录；LOSS保存逐来源审计并与已确认加工损耗核对 |
| `metal_production_wip_transfer` | 原加工记录→承接加工记录的实际件重及节点；关联逐来源分配 |
| 权限 | 新增可分配的`metal:production-batch:transform`按钮权限；不默认授予所有加工人员 |

来源表与分配表采用工厂范围复合外键；原领料分配增加factory/id唯一引用。数量、owner及件重非负约束与应用层多行守恒共同生效。

材料来源分为两条轴：当前owner决定仓库料权；历史供料来源决定客户料/厂供料构成。半成品当前全归客户，并不意味着原来的厂供料成分变成客户供料。

历史V82生产库存缺少精确来源时，不在GET或preview中补写、不根据当前owner猜来源。普通原料及新P3生产由真实领料和产出实时建立来源。旧NULL批次加工记录与历史报表保留兼容，新批次不能借此伪造历史映射。

### 3.1 守恒与事务

```text
各slice余额之和 = 原stock余额
每slice各owner余额之和 = 该slice余额
同stock、owner跨slice合计 = 原ownership余额
已纳入精确来源的slice：来源合计 = slice实物，且按currentOwner匹配料权
加工可用 = INPUT + carry-in - OUTPUT - RETURN - RECOVERY - carry-out - 已确认LOSS
```

写操作沿工厂锁及批次/加工/库存/来源/占用锁校验；身份、份额、来源、边、移交与幂等结果同事务。读报表采用只读快照，写事务保留当前锁定读。本轮真实HTTP联调发现并修复了只读事务误执行`FOR UPDATE`的问题。

## 5. 部分合并、再拆与差额

### 5.1 30＋70中的20

同事务完成必要拆分及合并：30全量参与，70来源显式指定20实物及`plannedQuantityForMerge=20`。生成B50、余量新身份50及中间参与身份；原70退出SPLIT，原30及中间参与身份退出MERGED。边保留“原70→参与20→B50”和“原70→剩余50”，不留下可继续领用的原70余额。

同stock的30/70份额也可合并，物理stock仍100，B50与余50使用不同slice。测试验证身份操作前后仓储事件数不变。

### 5.2 已合并后再拆10

合并结果的每个来源贡献仍独立保存。再次部分拆分缺少来源分配时拒绝；显式逐来源分配后形成10与90，保留父来源链。不宣称能追到每件物料的物理原子来源，记录的是用户确认的账面贡献及其依据。

### 5.3 目标100、实物98

隔离测试确认70件在工序二实际产出68件/680g，并核实报废2件/20g；关闭时将损耗逐来源消费，避免20g/2件仍留在可用在制。与30合并仅得到98件，计划仍100，正常批次完工拒绝，不隐藏缺口。

目前保留整批足额进入下一道的保护：尚未处理的目标缺口不能凭合并自动放行。需要继续生产或结算该差额时，须后续明确异常处置/补产目标流程，不在本阶段静默降低目标。

## 6. 原料责任、退料与余料承接

WIP分配保存本次真实issue授权与上游供料来源链。`carryAllocationId`证明当前加工记录承接的是哪份可退责任，不能只拿原issue总余额退料。

在制重量与未加工可退重量分别填写。可退责任默认0；明确确认20g/2件时，不能跨结果重复授予两次。当前加工用原issue退20后，可用在制700→680；超额再退拒绝；冲销恢复700及对应可退责任，历史30件产出来源不变。

若原生产来源已SPLIT/MERGED退出，原样退料不复活父批次：

1. 退料审核事务创建同一种生产批次，`origin_action=RETURN_RESIDUAL`，`planned_quantity=NULL`。
2. 继承原返回实物的完成节点。例如当前工序二退回的是工序一半成品，余料保持工序一阶段，不冒充工序二产出。
3. 同仓在原stock下建立新结果份额；异仓沿既有真实退料stock路径处理，保留原issue、真实RETURN及来源。
4. 不新增生产目标、OUTPUT或欠料；返回结果包含`residualBatchId`、`stockSliceId`及原来源引用。
5. 退料冲销检查下游及余额；无下游时反向恢复责任，余料结果标CANCELLED并保留反向操作，父批次仍退出。

仓储选项及明细编辑器已接入承接的原issue候选；同一原issue多份carry按carry ID区分，实际提交保留原issue与carry双引用。

## 7. API与前端

| 接口 | 语义 |
| --- | --- |
| `POST /metal/production-batches/splits/preview` | 纯预览，分配/阶段/占用/版本不符则业务失败，无写入 |
| `POST /metal/production-batches/splits` | PLAN_SPLIT、STOCK_SPLIT、PARTIAL_COMPLETION_WITH_WIP |
| `POST /metal/production-batches/merges/preview` | 同阶段全量/部分参与预览，显示余量身份及计划/实物两个维度 |
| `POST /metal/production-batches/merges` | FULL_MERGE、PARTIAL_MERGE，必要拆分与合并同事务 |
| `GET /metal/production-batches/{id}/context?intent=SPLIT或MERGE` | 当前版本、库存owner/source、WIP与可退责任、待办及操作原因 |
| `GET /metal/production-batches/operations/{requestId}` | 查询拆合原提交结果；未知仍为found=false，不能当作成功 |
| 既有仓储/工序接口 | 保留预占及审核；在制余额、退料、结束工序、报表及完工接入carry和移交状态 |

请求沿用P0字段：拆分sourceBatchId/Version、必要sourceExecutionId/Version、results；合并sources[]各自batch/version/stockAllocations及必要plannedQuantityForMerge。库存分配带stock/slice版本、netWeight、quantity及明确owner/source组成。提交需要UUID requestId、reason和拆合权限，同键不同内容拒绝。

前端新增拆合窗口、逐份额/owner/source分配编辑器；必须先预览，修改原因或分配后预览失效。未知结果沿用原请求查询/重试，不换新键。列表及详情展示原批次退出、承接记录、carry-in/out与加工历史。

P0完整结构化reasonCode/fieldErrors信封仍未全部落实，沿既有业务code/msg及界面原因显示。preview业务不合法时返回错误，不保证所有不合法请求都返回code200的allowed=false结构。
